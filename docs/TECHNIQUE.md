# Documentation technique

Détails pour développeurs : structure du projet, vérifications, publication, partie en ligne (Supabase) et rejeu vérifié. Retour à la [présentation du jeu](../README.md).

Jeu en GDScript sous Godot Engine (rendu Forward+ (Vulkan, repli OpenGL si Vulkan est absent) ; versions exécutables Windows et Linux uniquement, le Web est abandonné).

## Structure
- `data/` : données du jeu (config par défaut, talents, constantes, textes, niveaux de qualité)
- `assets/` : textures des 7 thèmes, icônes, portraits, planches (monstres, objets, torches)
- `scripts/core/` : chargement des données (autoload `Data`)
- `scripts/rules/` : moteur de règles sans affichage (formules de stats, puis combat, statuts…)
- `scenes/` : scènes Godot
- `data/quality_presets.json` : niveaux graphiques Faible / Moyen / Élevé / Ultra (menu « ⚙ Paramètres », autoload `Settings` : détection de la machine et adaptation automatique)

## Utilisation
Cloner le dépôt, ouvrir `project.godot` dans Godot 4.7, lancer le projet (F5).

## Sous-dossiers
- `scripts/rules/` : règles sans affichage (personnages, combat, générateur de donjon, état de partie, hasard et horloge déterministes, journal d'actions).
- `scripts/dungeon/` : couloir 3D (murs, portes, torches, brouillard, fontaines, sprites des monstres, salle de combat).
- `scripts/game/` : liaison entre règles et affichage (combat, actions, pièges et fenêtres de décision, monstres errants).
- `scripts/ui/` : fenêtres et interface (sac, forge, paramètres, comptes, défis, chat…).
- `scripts/core/` : services (données, textes, réglages graphiques, sauvegardes, son, mise à jour, compte en ligne, rejeu).
- `scripts/admin/` : éditeur de donjon et outils d'administration.
- `scenes/` : démarrage, accueil, partie, administration.
- `data/lang/` : textes français et anglais, guide et tutoriel ; `data/cloud_config.json` : configuration publique du compte en ligne.
- `assets/themes/` : textures des sept thèmes de décor (murs, sols, plafonds, fontaine) ; `monsters/` : sprites des monstres et boss ; `portraits/` : portraits des héros ; `icons/` : icônes d'objets, de sorts et de classes ; `ui/` : cadres, boutons, emplacements ; `home/` : écran d'accueil ; `fonts/`, `music/`, `sounds/` ; `sheets/` : planches d'objets et de monstres ; `misc/` : textures diverses (dont l'étal du marchand).
- `assets_src/` : images sources de l'épée (taille d'origine) ; seules les versions retaillées de `assets/ui/` sont exportées.
- `supabase/migrations/` : un fichier SQL par évolution du schéma, à appliquer dans l'ordre.
- `tools/` : `check_*` vérifications, `shot_*` captures, `gen_*` et `make_icon.py` génération de ressources, publication (versions, notes, paquets, VirusTotal), vérificateur des parties classées.
- `export_presets.cfg` : généré par `tools/gen_export_presets.py`.

## Vérifications
- Compilation : `godot --headless --path . res://tools/check_compile.tscn`
- Fenêtre de compte (sans réseau) : `godot --headless --path . res://tools/check_account.tscn`
- Textes : `python3 tools/check_lang.py`
- Réglages graphiques : `godot --headless --path . res://tools/check_settings.tscn`
- Mise en page mobile (aucun débordement à droite, carte masquée) : `godot --headless --path . res://tools/check_mobile.tscn`
- Touches du clavier (défauts par langue, réassignation, conflits, onglet Commandes) : `godot --headless --path . res://tools/check_keys.tscn`
- Effets de sorts avancés (choix de l'effet, repli, anciens sorts, paliers, lancer de chaque effet) : `xvfb-run -a godot --rendering-driver opengl3 --path . --script res://tools/check_spell_fx.gd`
- Version et journal : `python3 tools/check_version.py`
- Compte en ligne (sans réseau) : `godot --headless --path . res://tools/check_cloud.tscn`

## Versions et publication
- Le numéro de version est dans `project.godot` (`config/version`, forme `1.30.1`, ou `1.30.1-test1` pour un build de test). Le jeu l'affiche à partir de là (`AppVersion`).
- Journal des versions : `data/changelog.json` (affiché dans le jeu). Les notes de la publication GitHub en sont tirées (`tools/release_notes.py`).
- Publier : pousser sur `migration/donnees` un commit dont le message contient `[exe]` (préversion `v<version>`) ou `[release]` (publication normale). Le workflow « Publication » exporte Windows et Linux en **exécutable + paquets** (voir ci-dessous), crée ou met à jour la publication et y joint : l'installateur Windows (`...-setup.exe`), les installations complètes (`...-windows-full.zip`, `...-linux-full.tar.gz`), les fichiers un par un (`exe-*`, `core-*.pck`, `themes.pck`, `monsters.pck`, `audio.pck`) et les manifestes `manifest-<plateforme>.json` lus par la mise à jour du jeu.
- Disposition d'une installation : `Dungeon Generator.exe` (moteur seul) + `Dungeon Generator.pck` (code, données, polices, interface) + `packs/*.pck` (gros assets) + `install.json` (état des fichiers). Les groupes de paquets sont définis dans `tools/gen_export_presets.py` (qui régénère `export_presets.cfg`) ; `scripts/core/pack_loader.gd` monte `packs/*.pck` au démarrage.
- Mise à jour partielle (`scripts/core/updater.gd`) : le jeu lit le manifeste de la dernière publication et ne télécharge que les fichiers dont l'empreinte de contenu a changé. Essai complet : `sh tools/check_update_e2e.sh` (variable `GODOT`).
- Il n'y a plus d'export Web : le workflow d'envoi FTP a été supprimé (le site déjà en ligne n'est plus mis à jour).

## Partie en ligne (Supabase)
- Le jeu reste jouable hors ligne : rien n'est appelé au lancement. Le module de compte est l'autoload `Cloud` (`scripts/core/cloud.gd`) ; sa configuration (URL du projet + clé **publique**) est dans `data/cloud_config.json`. La clé secrète (`sb_secret_…` / `service_role`) ne va jamais dans le dépôt ni dans le jeu.
- Le schéma de la base est versionné dans `supabase/migrations/` (à appliquer dans l'ordre dans le SQL Editor du projet Supabase) : profils (pseudo public), donjons partagés (code DGZ1), signalements, challenges, parties soumises et classement. Les règles d'accès (RLS) bornent tout ce que la clé publique peut faire.
- Classement : le jeu envoie la graine et le journal d'actions de la partie (`runs`, statut `pending`), jamais un score cru sur parole. Un vérificateur de confiance, qui détient la clé secrète hors du dépôt, rejoue la partie et inscrit le score recalculé (`verified`) ; seul le classement des parties vérifiées est public (`leaderboard`).
- Défis (donjon aléatoire) : cliquer sur « Donjon aléatoire » ouvre d'abord la fenêtre des défis en cours avec leurs classements (`scripts/ui/challenges_modal.gd`), puis « Lancer un donjon aléatoire » mène aux réglages habituels. Un défi `declared` concerne les donjons aléatoires (pas de graine commune, donc pas de rejeu) : le jeu **déclare** son score (`scores`) et la base le borne par des contrôles de plausibilité (au moins 10 s de jeu par niveau, score qui ne baisse jamais, limites par jour) ; le classement public (`classement`) distingue les scores vérifiés (✔) des scores déclarés. Le suivi de partie (`levelsCleared`, `playSeconds`, `runId`, `adminUsed` dans `gs.stats`) et l'envoi sont dans `scripts/core/challenges.gd`. Une partie où l'administration a été ouverte n'est jamais envoyée. Un score trop incohérent se retire depuis le tableau de bord Supabase (table `scores`).
- Tests sans réseau : `godot --headless --path . res://tools/check_cloud.tscn` (compte), `res://tools/check_account.tscn` (fenêtre de compte), `res://tools/check_challenges.tscn` (défis, classement, envoi du score) ; suivi d'une vraie partie (affichage ou Xvfb requis) : `--script res://tools/check_run_tracking.gd`.
- Rejeu vérifié (en cours, étapes 1–4 faites) : toute la partie découle d'une graine texte (`Seeds`, `GameRng` : flux nommés combat/loot/trap/wander/village/ids, état sauvegardé avec la partie) et d'une horloge de jeu (`GameClock`, jamais l'heure réelle). Les actions du joueur sont journalisées dans `gs.run_log` (`RunLog`, entrées `[ms, commande, …]`) : déplacements, combat, objets (`Actions`), forge et Maître des Talents (village), et toutes les fenêtres de décision (`Flows` : fontaine, talents, évolution, piège et ses puzzles, boutique, marchand, victoire, village, modificateurs). Toute action non journalisée marque la partie « souillée » (`RunLog.unrecorded`) : elle n'est alors jamais classée. Le rejeu (`scripts/core/replayer.gd`) fait tourner la vraie scène du jeu et y injecte les commandes ; les règles d'acceptation vivent dans la logique partagée, pas dans l'interface. Tests : `check_determinism.tscn`, `check_game_rng.tscn` (valeurs de référence à confirmer sous Windows), `check_clock.gd`, et `xvfb-run -a godot --path . --script res://tools/check_replay.gd -- <graine> <actions> <niveaux>` (un bot joue une vraie partie, puis le journal est rejoué : l'empreinte de l'état doit être identique). Restent : règles des parties classées (ni administration, ni sauvegarde manuelle, ni retour arrière), vérificateur serveur et classement vérifié par mode de jeu.
- Parties classées par difficulté (serveur, étape 6a, pas encore branché à l'interface) : `supabase/migrations/20261010000200_parties_classees.sql` (réglages par difficulté `ranked_modes`, parties `ranked_runs`, fonctions `start_ranked_run` / `submit_ranked_run`, vue `classement_difficulte` vide tant que rien n'est vérifié). Côté jeu : `scripts/core/ranked_run.gd` (configuration partagée avec le vérificateur, démarrage, envoi, classement). Vérificateur : `tools/replay_run.gd` (rejoue un journal) + `tools/verify_runs.py` + workflow `.github/workflows/verify-runs.yml` (toutes les 15 min, secrets `SUPABASE_URL` et `SUPABASE_SECRET_KEY`, chaque partie est rejouée avec les règles de sa version, étiquette `v<version>`). Une partie classée n'accepte ni administration, ni export/import ; sa sauvegarde est à usage unique.
- Hardcore du mois (étape 6b) : `supabase/migrations/20261010000300_hardcore_mensuel_et_recompenses.sql`. Une graine par mois tirée par le serveur à la première partie du mois, difficulté hardcore, UN essai par jour (jour de Paris, consommé au lancement), classement `classement_periode` des parties vérifiées. Récompenses uniquement cosmétiques et de l'expérience : catalogue `badges` (titres, cadres, couleurs de pseudo), `player_badges`, `xp_log` / vue `account_xp` (niveau de compte), `player_cosmetics` + `equip_cosmetics`. Le vérificateur attribue tout (`award_run` après chaque partie vérifiée, `close_due_periods` pour les badges de rang des mois terminés depuis 2 jours), une seule fois. Côté jeu : section « Hardcore du mois » dans la fenêtre des défis du donjon aléatoire (`challenges_modal.gd`), `RankedRun.launch` / `submit` (journal gardé hors ligne puis renvoyé). Écrans : « Mes récompenses » (`rewards_modal.gd` : niveau de compte, collection de badges, équipement du titre, du cadre et de la couleur), « Parties classées » (`ranked_modal.gd` : un classement par difficulté + lancement), plaques de pseudo avec cadre (`cosmetics.gd`), accessibles depuis la fenêtre des défis et le compte. Tests sans réseau : `xvfb-run -a godot --path . --script res://tools/check_ranked_flow.gd` et `check_rewards_ui.gd`.
- Super admin (étape 6c) : `supabase/migrations/20261010000400_super_admin.sql`. Le rôle est une ligne de la table `admins` (aucune politique : illisible et inscriptible depuis le jeu ; on l'accorde par SQL depuis le tableau de bord : `insert into public.admins (player_id) values ('<uuid>')`). Chaque fonction `admin_*` revérifie le rôle côté serveur (`is_super_admin()`, erreur `acces_refuse`) : un jeu modifié n'obtient rien. Parties classées de TEST (`admin_start_ranked_run`, colonne `ranked_runs.test`) : n'utilisent pas l'essai du jour, exclues des classements, de l'XP, des badges et de la clôture des mois, mais rejouées par le vérificateur ; le Hardcore du mois de test garde les réglages du mois avec une graine aléatoire (la vraie graine n'est jamais révélée). Statistiques en lecture seule : `admin_overview`, `admin_players`, `admin_runs` (ni courriels ni journaux d'actions), et `admin_purge_tests`. Côté jeu : bouton « Super admin » dans la fenêtre Compte (affiché seulement si le serveur confirme le rôle), `super_admin.gd` / `super_admin_modal.gd`. Test sans réseau : `xvfb-run -a godot --path . --script res://tools/check_super_admin.gd`.

## Effets de sorts
- L'effet visuel d'un sort est indépendant de son `style` (école : le style décide aussi de la logique de combat, magique ou physique). Trois champs sur le sort : `fx` (identifiant d'effet, `classic` = effet d'origine en sprites, vide = effet par défaut du style), `fxTint` (couleur HTML, vide = couleur d'origine) et `fxPower` (0,6 à 2). `Data.ensure_defaults` les ajoute aux anciens sorts et aux sauvegardes.
- `scripts/dungeon/spell_fx_library.gd` (`SpellFxLibrary`) : catalogue des effets avancés (id, style et mode compatibles, script), teintes et intensités proposées, résolution de l'effet (effet inconnu ou incompatible = effet par défaut du style), palier de qualité, point d'entrée `cast`. `combat.gd` et `main.gd` y passent ; l'effet d'origine reste `SpellFxStyles.cast_spell`. Ajouter un effet = une entrée du catalogue + le script (une classe qui étend `spell_fx_kit.gd` avec une méthode `play(spell_id, target, ctx)`) + les textes `admin.spells.fx_*`. `SPELL_DEFAULT` associe à chaque sort d'origine son effet propre (résolution : effet choisi valide, sinon effet propre du sort, sinon premier effet du catalogue compatible avec le style et le mode, sinon classique).
- `scripts/dungeon/spell_fx_kit.gd` : boîte à outils commune des effets avancés (extraite d'Éclat Arcanique) : shaders (onde de choc face caméra ou à plat, lentille, orbe, rayon, plasma, roche en fusion, flamme et pilier à billboard vertical, trait de lame, dôme hexagonal), bruit de valeur 2D/3D, particules GPU (`_gpu`, `_pmat`, `_pmat_grow`, rubans), lumière dynamique, secousse, décalque générique `_glyph_decal`, et deux « moteurs » pilotés par dictionnaire : `_fly` (projectile : corps plasma, cristal ou maillage, halo, traînées, satellites, lentille, lampe) et `_hit_fx` (impact : éclair, ondes, éclats, rubans, étincelles, fumées additives ou sombres, décalque, lampe, secousse). `_c` fait tourner la palette de l'effet (`_base_hue`) vers la teinte choisie. `scripts/dungeon/spell_glyphs.gd` dessine les motifs gravés au sol (une texture 384 px par motif, en niveaux de gris multipliés par l'opacité).
- `scripts/dungeon/spell_fx_fire.gd` : boule de feu (plasma `SH_PLASMA` à bruit 3D qui défile, traînées de flammes, de fumée et de braises), météore (roche `SH_ROCK` : pierre sombre fendue de crêtes incandescentes, un météore par monstre en diagonale), colonne de feu (trois langues `SH_FLAME` superposées qui jaillissent d'une brûlure gravée au sol, tourbillon de braises en anneau, fumée au sommet, lampe qui gonfle puis s'éteint).
- Écoles : `spell_fx_ice.gd` (javelot, grêle : glaçons en volume et éclats), `spell_fx_holy.gd` (attaques sacrées et soins : piliers, sceaux au sol, lances, hélices de lumière, dôme), `spell_fx_shadow.gd` (sphères de vide, fumée noire, lames, pentagrammes, ciel d'apocalypse), `spell_fx_bard.gd` (notes en volume, portée, harpe, lune de la berceuse), `spell_fx_physical.gd` (coups de lame : traits `SH_STREAK`, étincelles et rubans, éclats de roche, sang, poison ; tirs : flèche en volume qui file ; plus les quatre sorts arcaniques de ralentissement et de flèches). `spell_glyphs.gd` dessine les motifs gravés (brûlure, givre, soleil, jugement, anathème, pentagramme). Chaque effet est une recette courte (`_fly` pour le projectile, `_hit_fx` pour l'impact) ; `SPELL_DEFAULT` associe chaque sort d'origine à son effet, les sorts créés dans l'éditeur reprennent l'effet par défaut de leur école et de leur mode. Noms de méthodes d'un script d'école : ne jamais reprendre celui d'une méthode du parent.
- École de nature : `spell_fx_nature.gd` (feuilles et pétales en textures procédurales, épine et lianes en maillages `SurfaceTool` avec ombrage cuit dans les couleurs de sommets, éclair en segments `_beam` qui se recouvrent, nuée de particules à forte turbulence) ; six sorts dans `data/default_config.json` (`spell_nature1` à `6`, style `nature`, aucun n'est attribué à une classe pour l'instant : les monstres peuvent les tirer comme capacité, le créateur les attribue). Migration des sauvegardes et configurations (schéma 8 → 9, `SaveMigrations._v8_to_v9`) : les sorts du jeu manquants sont ajoutés, sans dupliquer ni écraser un sort existant, sauf dans un donjon personnalisé ; testé par `tools/check_saves.tscn`.
- Capacités des monstres : `combat.gd` (`_monster_use_ability`) ajoute à l'événement `fx3d` un contexte `fromMonster: true` avec `victim` (place du héros visé, 0 à 3) ; `SpellFxLibrary.cast` le route vers `spell_fx_monster.gd` (étend le script de nature pour réutiliser ses briques) : le sort part du monstre (point visé de `CombatStage.target_point`) vers la place du héros (`_slot_pos`). Quatre familles choisies d'après l'effet du sort (`RAIN_FX`, `BURST_FX`, `CLAW_FX`, sinon projectile) et la palette de l'école. Sans rendu avancé (palier 0 ou pas Forward+), seule l'animation du coup reçu joue (l'effet d'origine tire vers les monstres, pas vers le groupe). Les graines de partie d'une version à l'autre ne donnent plus les mêmes donjons : le générateur tire les capacités dans la liste des sorts de dégâts, qui s'est allongée.
- Classe Druide : `class_druid` (base, bâton et masse, sorts nature 1, 5 et 2 aux niveaux 1, 3 et 6) évolue au niveau 5 en `class_warden` (Gardien de la Forêt : soins et protection, sorts aux niveaux 7, 13, 20, 27) ou `class_stormcaller` (Druide de la Tempête : dégâts de zone, mêmes niveaux). Cinq sorts de nature de plus (`spell_nature7` à `11` : écorce protectrice `shieldSingle`, sève régénérante `healSingle`, arbre-monde `healParty`, ouragan de feuilles et colère de la nature `damageGroup`) avec leurs effets (`nature_bark`, `nature_sap`, `nature_worldtree`, `nature_cyclone`, `nature_wrath` : tronc `SurfaceTool` qui pousse, couronne de feuillage persistante `_crown`, couronne de lianes `_vine_ring`). Talents : `data/class_talents.json` (5 paliers de 2 choix par classe). Le nom « Druide » est déclaré partout où existe la liste des classes de base : `AdminUtil.BASE_ARCHETYPES`, `Data.BASE_EVOLUTIONS`, `Saves._base_class`, `IconPicker.PORTRAIT_CLASSES`, `DungeonGenerator.ARCHETYPE_STATS`, `PORTRAIT_COUNTS`, `PORTRAIT_FILES` (une classe oubliée dans l'une de ces listes manque à la génération aléatoire ou aux talents). Icônes : `tools/gen_druid_icons.py` écrit les 3 icônes de classe et les 11 icônes de sorts de nature (`spell_nature1` à `11`, qui remplacent les anciens emoji). Portraits : `druide_0` à `4` sont des copies d'illustrations existantes (cerf feuillu, orc chaman, rôdeuse à capuche de feuilles, guerrière aux peintures vertes, mage de foudre) ; `PORTRAIT_TWINS` empêche de voir la même image deux fois dans un groupe (une classe évoluée reprend le portrait de sa classe de base d'après `evolvesFrom`). Pour de nouveaux visuels, déposer `druide_5.webp`… (128×128) et augmenter `PORTRAIT_COUNTS["Druide"]`. Migration (schéma 9 → 10, `SaveMigrations._v9_to_v10`) : ajoute les trois classes et les sorts manquants (jamais dans un donjon personnalisé, jamais si une classe du créateur porte déjà le même identifiant ou le même nom) et passe les icônes emoji des sorts de nature à l'image seulement si le créateur ne les avait pas changées ; testée par `tools/check_saves.tscn`. Contrôle de la classe : `tools/check_druid.tscn`. Les graines de partie ne redonnent plus les mêmes groupes : le Druide entre dans le tirage des classes de base.
- Paliers (`SpellFxLibrary.tier`, d'après les options graphiques) : 0 sans halo (`fx_glow` désactivé) = effet d'origine ; 1 = particules GPU, halo HDR ; 2 = + lumière dynamique qui éclaire la brume, rune au sol (option `fx_decals`) ; 3 (Ultra, `particles` ≥ 1,25) = + lentille de distorsion. Rendu non Forward+ : effet d'origine. Le script de l'effet est chargé à l'exécution ; s'il ne se charge pas, l'effet d'origine joue à la place.
- `scripts/dungeon/spell_fx_arcane.gd` (palette violette de base tournée par défaut vers le bleu, `DEFAULT_HUE`) : cristal, orbe de mana et rayon (shaders d'onde de choc, de lentille, d'orbe et de rayon ; rubans de particules GPU ; décalque de cercle runique (futhark ancien dessiné par traits dans une texture 512 px, couleur multipliée par l'opacité car l'émission du décalque ignore l'alpha) ; secousse de caméra désactivée par « mouvement réduit »). Le contrat avec le combat est conservé (`SpellFx3D.busy`, `wait_idle`) ; les shaders sont précompilés par `warm_up.gd`.
- Éditeur : colonne « Style (animation) » de l'onglet Sorts (`admin_spells.gd`) avec effet, teinte, intensité et bouton « Aperçu » (`scripts/ui/spell_fx_preview.gd` : petite scène 3D à trois mannequins, avec repères des quatre places du groupe ; le contexte transmis contient les trois cibles, l'allié (place 2) et le lanceur (place 3), si bien que les effets de groupe et de soin sont montrés comme en combat ; effet joué en boucle avec les réglages graphiques actuels).
- Les capacités spéciales des monstres (sorts de dégâts tirés au hasard) ne jouent pas d'effet de sort, seulement l'animation du coup reçu.

## Interface de jeu (colonne de droite et menu du haut)
Écart voulu avec la page d'origine, où le menu « 💾 Sauvegarde » était un panneau en bas de la colonne de droite et le grimoire un petit panneau (2 lignes visibles à 1920×1080).
- Menu du haut : `SaveMenu` (`save_menu.gd`) est hébergé par `AppHeader.add_save_menu` (`app_header.gd`), entre « Paramètres » et « Compte ». Il n'existe qu'en jeu (l'accueil n'en a pas). La liste s'ouvre sous le bouton, large d'au moins 300 px de conception et recadrée dans l'écran ; le groupe de boutons du haut reste déployé tant qu'elle est ouverte (`SaveMenu.is_open`). En combat le bouton est inerte et grisé (`locked`, `GameLayout._process`). Les refus des parties classées (pas de sauvegarde, d'export ni d'import) restent dans `main.gd` (`_on_menu`). Sur mobile (portrait) le bouton n'affiche que l'icône 💾.
- Colonne de droite (`GameLayout._rebuild`, paysage) : Carte, Besace, Grimoire. Le panneau « Menu » n'existe plus (ni son onglet en portrait, qui garde Besace et Journal). La besace garde la taille de son contenu (`SIZE_SHRINK_BEGIN`) et le grimoire prend tout le reste de la colonne (`SIZE_EXPAND_FILL`). La police du journal (`LogPanel`) passe de 14 px à 0,9 rem (≈ 16 px ; 0,8 rem en portrait).
- Carte repliable : bouton ▾/▸ à gauche du titre du panneau (le bouton 🗺️ « plein écran » reste à droite) ; replié, il ne reste que le titre et le grimoire occupe la place libérée. L'état est `GameLayout.map_folded` (variable statique) : il vaut pour la session et ne fait partie ni des sauvegardes ni des configurations, donc aucune migration (le schéma reste 10). Textes : `ui.game_layout.replier_la_carte` et `ui.game_layout.deplier_la_carte`.

## Fenêtre du marchand (`scripts/ui/shop_modal.gd`)
Sélection : chaque carte a une clé (`_gkey`) ; les piles (potions, parchemins identiques) se regroupent par `Inventory.stack_key`, mais un objet non empilable est désigné par son indice dans la besace, car deux exemplaires d'une même définition partagent le même `id` (ancien bug : en vendre un en sélectionnait un autre). Le bouton Acheter/Vendre, avec son prix, est tout en haut de la fiche (sous le titre), suivi du motif de refus, de la quantité (piles) et des caractéristiques. Sélection multiple (onglet Vendre, bouton « ☑ Sélection multiple », ou Ctrl/Maj + clic) : cartes cochées ☐/✓, « Tout sélectionner/désélectionner », total en or, une seule transaction par objet via `Flows.input("shop", …)` (donc journalisée et rejouable) ; les clés sont refusées. État d'interface seulement : aucune migration de sauvegarde (schéma inchangé).

## Commandes (couloir 3D)
Boutons à l'écran (tactile) ou clavier, touches physiques : ↑/Z avancer, ↓/S reculer, Q/D pas de côté, ←/A et →/E tourner (libellés AZERTY).

## Icône du jeu
- Source : l'épée du jeu (`assets/ui/sword_loading_padded.png`) ; `python3 tools/make_icon.py` régénère `assets/app_icon.png` (icône du projet : fenêtre et barre des tâches sous Windows et Linux), `installer/app.ico` et `installer/app_icon_256.png`.
- Windows : le workflow de publication applique `installer/app.ico` et les informations de version à l'exécutable avec rcedit sous Wine (`tools/patch_windows_exe.sh`, vérifié par `tools/check_exe_icon.py` : simple avertissement en cas d'échec) ; l'installateur Inno Setup, ses raccourcis et la désinstallation utilisent la même icône (`installer/app.ico`).
- Linux : l'exécutable ELF ne porte pas d'icône ; l'archive complète contient `Dungeon Generator.png` et `install-menu.sh` (entrée du menu des applications avec l'icône, sans droits administrateur ; `--remove` pour la retirer).


### Compteur de performances
`scripts/core/perf_overlay.gd` : un seul `Label` (couche 120) en haut à gauche, sans panneau ni cadre ; lisibilité assurée par un liseré de texte sombre. Une ligne : images/s, RAM, VRAM, appels de dessin (couleur selon les images/s). F3 ou bouton 📊.
Taille constante : la ligne est compensée par le rapport entre l'échelle de la scène de jeu (zone de conception 1600 x 1000) et l'échelle courante (`content_scale_factor`), donc elle garde la taille qu'elle a dans le donjon au lancement et dans le menu d'accueil.

## Pièges : pointes au sol
`scripts/dungeon/trap_spikes.gd` (`TrapSpikes`) : le piège `spikes` est un vrai volume, plus un décalque. Un maillage unique (`ArrayMesh`, construit par `SurfaceTool` puis partagé par tous les pièges) : surface 0 = plaque de fer biseautée, rivets et douilles (normales explicites) ; surface 1 = 25 pointes d'acier à trois anneaux (hauteurs et inclinaisons variées, dégradé rouille → acier, quelques-unes tachées de sang), normales lissées. Elles projettent des ombres sous la lumière des torches. Une ombre de contact douce (texture générée) noircit le sol autour. `TrapDecals.make_mesh("spikes")` y renvoie ; la vapeur, les fléchettes, la fosse et la rune ont leur propre modèle (sections suivantes) : plus aucun piège n'est un décalque.
Les pointes forment un nœud enfant `Spikes` : quand le piège est désamorcé (`Interactions._trap_resolved`), `EntityLayer.disarm_item` appelle `TrapSpikes.retract` (écrasement progressif en 0,5 s dans la plaque, qui reste en place) ; au chargement d'un niveau (`main.gd`), l'état « désamorcé » des sauvegardes rentre les pointes tout de suite, sans animation, donc rien à migrer. Les autres pièges disparaissent comme avant.

## Pièges : vapeur verte
`scripts/dungeon/trap_gas.gd` (`TrapGas`) : bouche d'aération de fer (maillage `SurfaceTool`, mêmes briques `TrapSpikes.add_box` / `add_prism`) et nuage vert épais en continu : trois émetteurs `GPUParticles3D` (colonne de volutes, nappe rasante qui coule sur le sol, cœur lumineux additif en HDR pour le halo de l'environnement), turbulence, bouffées en texture de nuage générée (bruit simplex), `proximity_fade` (Forward+) pour estomper les bouffées au contact du sol et des murs ; lueur verte pulsante (`OmniLight3D`, sans composante spéculaire : sur un sol mouillé elle dessinait une traînée verte brillante sous la bouche) et brume volumétrique verte (`FogVolume`, Forward+ uniquement). Le nombre de particules suit l'option `particles`. Les particules sont préchauffées (`preprocess`) : le nuage est déjà formé à l'apparition. `TrapGas.stop` (piège désamorcé, `EntityLayer.disarm_item`) coupe les émetteurs, éteint la lueur et dissipe la brume en quelques secondes ; au chargement d'un niveau déjà désamorcé, le nuage n'est pas créé. `warm_up.gd` précompile les deux pièges.

### Sons des pièges qui se déclenchent
Un son propre à chaque type de piège, joué seulement quand le piège se déclenche pour de bon, c'est-à-dire quand la dernière tentative échoue (jet raté d'une méthode qui résout le piège, échec simple ou critique, ou puzzle raté) : `Sound.TRAP_FAIL_SOUNDS` (`spikes` → `trap_snap.ogg`, `gas` → `steam_hiss.ogg`, `dart` → `dart_swish.ogg`, `pit` → `wood_thud.ogg`, `rune` → `rune_seal.ogg`) ; un type sans son attitré joue le coup habituel (`hit`). `Sound.trap_fail(kind)` est appelé par `TrapModal._roll_outcome` avec le type du piège ; un jet de sonde raté, lui, ne déclenche rien et laisse un nouveau choix : il ne joue pas ce son (`TrapModal._roll_outcome` ignore la sonde). Chaque fichier est converti du MP3 fourni en OGG et atténué à l'export pour atteindre -20 LUFS (comme `dice.ogg`), avec un gain `SFX_GAIN_DB` de -14 (même méthode que tous les effets : cible -34 LUFS, `tools/sfx_levels.py`). Règle pour tout nouveau son : le mesurer avec `tools/sfx_levels.py` et reporter son gain dans `SFX_GAIN_DB`.

Parcours des récompenses (onglet « Récompenses » du hub en ligne, `online_hub.gd`, `_rw_render`) : les récompenses déjà obtenues par le joueur sont listées en premier, puis celles à obtenir ; dans chaque groupe, par rareté croissante, puis dans l'ordre du catalogue.

Brume en combat (`fog_mist.gd`) : dans les niveaux à brouillard, la brume volumétrique et le brouillard général se dissipent pendant un combat (il reste 15 % de la brume volumétrique et 25 % du brouillard général, `COMBAT_VOLUME` / `COMBAT_GENERAL`) puis reviennent à la fin, en fondu d'environ 1,7 s. `main.gd` fournit `combat_probe` (combat à l'écran : `level_node.stage.active`). Effet purement visuel ; en exploration le facteur vaut 1, rien ne change.

Piège de vapeur permanent : une réussite le désamorce (la vapeur cesse, la dalle reste) ; un échec laisse le nuage en place, le groupe peut avancer, mais s'il repasse sur la dalle un nouveau défi se déclenche (même mécanique que les pointes : `permanent`, `Interactions._apply_trap_hits`). Le générateur et le donjon d'origine créent la vapeur avec `permanent: true`. Migration des sauvegardes et configurations (schéma 3 → 4, `SaveMigrations._v3_to_v4`) : les pièges de vapeur existants (niveaux et bibliothèque) deviennent permanents, une seule fois ; testé par `tools/check_saves.tscn`.

Commandes en attente (parties classées, `main.gd`) : une commande n'est acceptée qu'au repos (`settled()`), donc pendant un effet en cours (fontaine, coup…) un déplacement ou un quart de tour était perdu : il fallait appuyer deux fois. Désormais la dernière commande de déplacement est gardée trois secondes (`PENDING_MS`) et exécutée dès que le jeu est au repos ; elle est journalisée à ce moment-là, comme si le joueur appuyait à cet instant, donc le rejeu reste identique (`check_determinism`, `check_replay` OK).

Personnage à terre (PV à 0) : son portrait passe en niveaux de gris, anneau compris (`UiTheme.circle_gray_material`, paramètre `gray` de `UiTheme.portrait` et de `EquipDock._round_medal`) dans la rangée de portraits en haut de l'équipement, au centre de l'équipement et dans la fiche du personnage (`PartyModal`).
La brume se dissipe de la même façon quand le groupe est à deux cases ou moins du marchand ambulant (distance de Manhattan, y compris debout devant son étal dans la niche) : même facteur et même fondu que pendant un combat, retour à la normale en s'éloignant.

Icônes de classes : chaque classe fournie par le jeu doit avoir une icône en image (`@icon:…`). Les anciennes configurations et sauvegardes avaient parfois un emoji ou une icône introuvable sur des classes évoluées (le choix d'évolution n'affichait alors rien, ex. le Voleur). `SaveMigrations.repair_class_icons` redonne l'icône du jeu à ces classes ; elle est appliquée par la migration v4 → v5 (classes, héros qui portaient l'ancienne icône de leur classe, héros de la sauvegarde) et à chaque chargement de configuration (`Data.ensure_defaults`). Les classes créées par le joueur et les icônes de héros choisies à la main ne sont jamais touchées. Dans l'éditeur, une nouvelle classe reçoit une icône en image (bouclier, ou celle de la classe dont elle dépend pour une évolution) au lieu d'un emoji. Testé par `tools/check_saves.tscn`.

## Pièges : fléchettes murales
`scripts/dungeon/trap_dart.gd` (`TrapDart`) : le piège `dart` est un mécanisme fixé au mur, plus un décalque. `EntityLayer.populate` choisit le mur voisin de la dalle du piège (`LevelBuilder.dart_wall_dir` : jamais un mur évidé par une niche de fontaine ou de marchand, ni un creux voisin ; stable d'après l'identifiant ; `LevelBuilder.niche_data` partage ce calcul avec la construction du niveau) et y pose le modèle, orienté par `TrapDart.yaw_for`. Les torches sont au centre des pans de mur des cases où x + y est pair, à 2,48 m : sur ces cases la plaque est posée plus bas (`LevelBuilder.dart_height`, 1,15 m au lieu de 1,5 m) pour ne pas la chevaucher, et la dalle reste au sol quelle que soit la hauteur (nœud `Slab` à part) ; un piège à fléchettes ne peut exister que contre un mur : `DungeonGenerator.build_config` ne le pose que sur une case adossée à un mur (jamais à une intersection ; à défaut, des pointes) et `EntityLayer.populate` transforme en pointes (`trapKind: spikes`) tout piège à fléchettes d'un niveau existant (donjon personnalisé, sauvegarde) dont la case n'a aucun mur utilisable ou qui est en plein air. Vérifié sur 25 donjons générés (53 pièges à fléchettes, tous contre un mur). Repère local : l'origine est sur le mur, +Z va vers le couloir. Un maillage partagé (`SurfaceTool`, briques `TrapSpikes.add_box`) : encadrement de pierre, tôle de fer rivetée, huit trous cerclés (2 × 4) et la dalle de déclenchement au sol, sur la case du piège ; huit fléchettes (hampe de bois, pointe d'acier, empennage rouge) forment un nœud à part `Darts`. Le piège est proposé quand le groupe arrive sur la dalle (déclenchement habituel d'un piège sur sa case). Piège permanent (`permanent: true`) : une réussite le désamorce (`TrapDart.retract` : les fléchettes rentrent, les trous restent vides, la plaque reste au mur) ; un échec tire une salve (`EntityLayer.fire_item`, appelé par `Interactions._apply_trap_hits` : volée qui traverse le couloir en 0,2 s, puis rechargement) et le piège reste actif pour un nouvel essai si le groupe repasse sur la dalle. Au chargement d'un niveau déjà désamorcé, les fléchettes ne sont pas affichées. Le son de l'échec est `dart_swish.ogg` (converti du MP3 fourni, gain `SFX_GAIN_DB` -13,5 mesuré par `tools/sfx_levels.py`, cible -34 LUFS). Migration des sauvegardes et configurations (schéma 5 → 6, `SaveMigrations._v5_to_v6`, qui partage `_make_permanent` avec la vapeur) : les pièges à fléchettes existants (niveaux et bibliothèque) deviennent permanents ; testé par `tools/check_saves.tscn`. `warm_up.gd` précompile le modèle.

## Pièges : fosse béante
`scripts/dungeon/trap_pit.gd` (`TrapPit`) : le piège `pit` est un vrai trou dans le sol, en haute définition. `LevelBuilder.build` repère les cases portant une fosse (`pits`) et `LevelBuilder._floor_cell` y découpe le sol en quatre bandes autour d'un trou carré de `TrapPit.HALF` (0,85 m) de demi-côté (mêmes UV que le sol plein, valable aussi pour les chemins en plein air). Le nœud du piège (`TrapPit.make(theme)`, posé au niveau du sol au centre de la case) contient un maillage à quatre surfaces : (0) parois maçonnées en assises de blocs taillés sur un fond de mortier sombre (hauteurs et largeurs variées, joints décalés, face avant en retrait irrégulier et quatre chanfreins par bloc, plus sombre en descendant) ; (1) rochers : cubes subdivisés ramenés sur une sphère et déformés par du bruit, posés au sol, normales lissées ; (2) margelle de dalles ébréchées (deux couches : le dessus en retrait fait le biseau) ; (3) pieux du fond (`TrapSpikes._spike`, acier du piège de pointes). Le hasard est à graine fixe : toutes les fosses sont identiques. **Matériaux du thème** : `TrapPit._stone` copie les matériaux mur et sol de `ThemeMaterials.for_theme` du niveau en cours (couleur, normales, occlusion et rugosité pour la pierre ; pixel-art pour damp, lava et temple), les projette en triplanaire (le maillage n'a pas d'UV ; échelle déduite de celle du thème), coupe le relief par parallaxe et laisse les couleurs de sommet assombrir la profondeur : les parois et blocs prennent le mur, la margelle et les rochers le sol, la fosse se fond donc dans le couloir. Une faible `OmniLight3D` froide au fond (`Depth`) évite que l'ombre du bord noie la fosse. Planches (`Planks`, cachées tant que le piège est actif) : cinq planches à arête chanfreinée, deux traverses, deux sangles et des clous de fer ; bois texturé (veinage, cernes, pores, nœuds) en couleur et normales 1024 x 1024 (`assets/misc/pit_wood_albedo.jpg` et `pit_wood_normal.png`, fabriquées par `tools/make_pit_wood.gd` ; relancer ce script pour les régénérer). Piège permanent (`permanent: true`) : une réussite le désamorce (`TrapPit.cover`, appelé par `EntityLayer.disarm_item` : les planches tombent en travers du trou, la lueur du fond est retirée, immédiat au chargement d'un niveau déjà désamorcé) ; un échec laisse la fosse ouverte et le groupe peut avancer, mais s'il repasse sur la case un nouveau défi se déclenche. Le son de l'échec est `wood_thud.ogg` (converti du MP3 fourni, rehaussé de 8 dB avec limiteur car la source est faible, gain `SFX_GAIN_DB` -13,5, cible -34 LUFS). Migration des sauvegardes (schéma 6 → 7, `SaveMigrations._v6_to_v7`, via `_make_permanent`) : les fosses existantes (niveaux et bibliothèque) deviennent permanentes ; testé par `tools/check_saves.tscn`. `warm_up.gd` précompile le modèle (la fosse du mini-niveau passe par `EntityLayer`).

## Pièges : rune de flammes
`scripts/dungeon/trap_rune.gd` (`TrapRune`) : le piège `rune` est le dessin du cercle magique du sort Éclat Arcanique (`SpellFxArcane._rune_tex`, texture partagée et mise en cache : anneaux, 24 runes du futhark, hexagramme) posé à plat sur un plan additif, teinté orange en HDR (elle nourrit le halo de l'environnement) et pulsant en boucle (tween sur la couleur et sur la lueur). Autour : une trace de brûlure sombre sous le dessin, un halo orangé au ras du sol, des braises qui montent le long des anneaux (`GPUParticles3D` en anneau, nombre suivant l'option `particles`) et une `OmniLight3D` orangée sans spéculaire. `TrapRune.fire` (échec du jet, appelé par `EntityLayer.fire_item`) lance une gerbe de flammes (`GPUParticles3D` à tir unique, additives, bouffées `TrapGas._puff_tex`), un éclair de lumière et une surbrillance des runes, puis le cercle se rallume. `TrapRune.stop` (piège désamorcé, `EntityLayer.disarm_item`) coupe la pulsation et toute gerbe en cours (sans quoi elle rallumerait les runes), éteint les runes (elles restent gravées, sombres), les braises, le halo et la lueur ; immédiat au chargement d'un niveau déjà désamorcé. Piège permanent : un échec laisse le piège actif (même mécanique que les pointes). Le son de l'échec est `rune_seal.ogg` (converti du MP3 fourni, gain `SFX_GAIN_DB` -13, cible -34 LUFS). Migration des sauvegardes (schéma 7 → 8, `SaveMigrations._v7_to_v8`, via `_make_permanent`) : les pièges à runes existants (niveaux et bibliothèque) deviennent permanents ; testé par `tools/check_saves.tscn`. Présence dans tous les types de donjon : le générateur (donjons aléatoires et création) tire la rune parmi `TRAP_KINDS`, et le donjon d'origine (`data/default_config.json`) reçoit deux runes et trois fosses (trap6 à trap10, permanentes) en plus de ses pointes, fléchettes et vapeur. Les parties déjà commencées gardent leurs niveaux tels quels (seule la permanence des pièges existants est migrée) ; les nouveaux pièges du donjon d'origine apparaissent dans les nouvelles parties. `warm_up.gd` précompile les quatre modèles.
