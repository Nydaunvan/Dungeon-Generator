# Documentation technique

Détails pour développeurs : structure du projet, vérifications, publication, partie en ligne (Supabase) et rejeu vérifié. Retour à la [présentation du jeu](../README.md).

Jeu en GDScript sous Godot Engine (rendu Forward+ (Vulkan, repli OpenGL si Vulkan est absent) ; versions exécutables Windows et Linux uniquement, le Web est abandonné).

## Structure
- `data/` : données du jeu (config par défaut, talents, constantes, textes, niveaux de qualité)
- `assets/` : textures des 7 thèmes, icônes, portraits, planches (monstres, objets, torches)
- `scripts/core/` : chargement des données (autoload `Data`)
- `scripts/rules/` : moteur de règles sans affichage (formules de stats, puis combat, statuts…)
- `scenes/` : scènes Godot
- `data/quality_presets.json` : niveaux graphiques Faible / Moyen / Élevé / Ultra (menu « ⚙ Paramètres », autoload `Settings` : détection de la machine et adaptation automatique)

## Utilisation
Cloner le dépôt, ouvrir `project.godot` dans Godot 4.7, lancer le projet (F5).

## Sous-dossiers
- `scripts/rules/` : règles sans affichage (personnages, combat, générateur de donjon, état de partie, hasard et horloge déterministes, journal d'actions).
- `scripts/dungeon/` : couloir 3D (murs, portes, torches, brouillard, fontaines, sprites des monstres, salle de combat).
- `scripts/game/` : liaison entre règles et affichage (combat, actions, pièges et fenêtres de décision, monstres errants).
- `scripts/ui/` : fenêtres et interface (sac, forge, paramètres, comptes, défis, chat…).
- `scripts/core/` : services (données, textes, réglages graphiques, sauvegardes, son, mise à jour, compte en ligne, rejeu).
- `scripts/admin/` : éditeur de donjon et outils d'administration.
- `scenes/` : démarrage, accueil, partie, administration.
- `data/lang/` : textes français et anglais, guide et tutoriel ; `data/cloud_config.json` : configuration publique du compte en ligne.
- `assets/themes/` : textures des sept thèmes de décor (murs, sols, plafonds, fontaine) ; `monsters/` : sprites des monstres et boss ; `portraits/` : portraits des héros ; `icons/` : icônes d'objets, de sorts et de classes ; `ui/` : cadres, boutons, emplacements ; `home/` : écran d'accueil ; `fonts/`, `music/`, `sounds/` ; `sheets/` : planches d'objets et de monstres ; `misc/` : textures diverses (dont l'étal du marchand).
- `assets_src/` : images sources de l'épée (taille d'origine) ; seules les versions retaillées de `assets/ui/` sont exportées.
- `supabase/migrations/` : un fichier SQL par évolution du schéma, à appliquer dans l'ordre.
- `tools/` : `check_*` vérifications, `shot_*` captures, `gen_*` et `make_icon.py` génération de ressources, publication (versions, notes, paquets, VirusTotal), vérificateur des parties classées.
- `export_presets.cfg` : généré par `tools/gen_export_presets.py`.

## Vérifications
- Compilation : `godot --headless --path . res://tools/check_compile.tscn`
- Fenêtre de compte (sans réseau) : `godot --headless --path . res://tools/check_account.tscn`
- Textes : `python3 tools/check_lang.py`
- Réglages graphiques : `godot --headless --path . res://tools/check_settings.tscn`
- Mise en page mobile (aucun débordement à droite, carte masquée) : `godot --headless --path . res://tools/check_mobile.tscn`
- Touches du clavier (défauts par langue, réassignation, conflits, onglet Commandes) : `godot --headless --path . res://tools/check_keys.tscn`
- Effets de sorts avancés (choix de l'effet, repli, anciens sorts, paliers, lancer de chaque effet) : `xvfb-run -a godot --rendering-driver opengl3 --path . --script res://tools/check_spell_fx.gd`
- Version et journal : `python3 tools/check_version.py`
- Compte en ligne (sans réseau) : `godot --headless --path . res://tools/check_cloud.tscn`

## Versions et publication
- Le numéro de version est dans `project.godot` (`config/version`, forme `1.30.1`, ou `1.30.1-test1` pour un build de test). Le jeu l'affiche à partir de là (`AppVersion`).
- Journal des versions : `data/changelog.json` (affiché dans le jeu). Les notes de la publication GitHub en sont tirées (`tools/release_notes.py`).
- Publier : pousser sur `migration/donnees` un commit dont le message contient `[exe]` (préversion `v<version>`) ou `[release]` (publication normale). Le workflow « Publication » exporte Windows et Linux en **exécutable + paquets** (voir ci-dessous), crée ou met à jour la publication et y joint : l'installateur Windows (`...-setup.exe`), les installations complètes (`...-windows-full.zip`, `...-linux-full.tar.gz`), les fichiers un par un (`exe-*`, `core-*.pck`, `themes.pck`, `monsters.pck`, `audio.pck`) et les manifestes `manifest-<plateforme>.json` lus par la mise à jour du jeu.
- Disposition d'une installation : `Dungeon Generator.exe` (moteur seul) + `Dungeon Generator.pck` (code, données, polices, interface) + `packs/*.pck` (gros assets) + `install.json` (état des fichiers). Les groupes de paquets sont définis dans `tools/gen_export_presets.py` (qui régénère `export_presets.cfg`) ; `scripts/core/pack_loader.gd` monte `packs/*.pck` au démarrage.
- Mise à jour partielle (`scripts/core/updater.gd`) : le jeu lit le manifeste de la dernière publication et ne télécharge que les fichiers dont l'empreinte de contenu a changé. Essai complet : `sh tools/check_update_e2e.sh` (variable `GODOT`).
- Il n'y a plus d'export Web : le workflow d'envoi FTP a été supprimé (le site déjà en ligne n'est plus mis à jour).

## Partie en ligne (Supabase)
- Le jeu reste jouable hors ligne : rien n'est appelé au lancement tant qu'aucun compte n'est connecté (un joueur connecté envoie seulement son signal de présence, ci-dessous, et un échec est ignoré). Le module de compte est l'autoload `Cloud` (`scripts/core/cloud.gd`) ; sa configuration (URL du projet + clé **publique**) est dans `data/cloud_config.json`. La clé secrète (`sb_secret_…` / `service_role`) ne va jamais dans le dépôt ni dans le jeu.
- Le schéma de la base est versionné dans `supabase/migrations/` (à appliquer dans l'ordre dans le SQL Editor du projet Supabase) : profils (pseudo public), donjons partagés (code DGZ1), signalements, challenges, parties soumises et classement. Les règles d'accès (RLS) bornent tout ce que la clé publique peut faire.
- Classement : le jeu envoie la graine et le journal d'actions de la partie (`runs`, statut `pending`), jamais un score cru sur parole. Un vérificateur de confiance, qui détient la clé secrète hors du dépôt, rejoue la partie et inscrit le score recalculé (`verified`) ; seul le classement des parties vérifiées est public (`leaderboard`).
- Défis (donjon aléatoire) : cliquer sur « Donjon aléatoire » ouvre d'abord la fenêtre des défis en cours avec leurs classements (`scripts/ui/challenges_modal.gd`), puis « Lancer un donjon aléatoire » mène aux réglages habituels. Un défi `declared` concerne les donjons aléatoires (pas de graine commune, donc pas de rejeu) : le jeu **déclare** son score (`scores`) et la base le borne par des contrôles de plausibilité (au moins 10 s de jeu par niveau, score qui ne baisse jamais, limites par jour) ; le classement public (`classement`) distingue les scores vérifiés (✔) des scores déclarés. Le suivi de partie (`levelsCleared`, `playSeconds`, `runId`, `adminUsed` dans `gs.stats`) et l'envoi sont dans `scripts/core/challenges.gd`. Une partie où l'administration a été ouverte n'est jamais envoyée. Un score trop incohérent se retire depuis le tableau de bord Supabase (table `scores`).
- Session mémorisée : `Cloud.request(..., auth=true)` renouvelle le jeton avant la requête s'il expire dans moins de 60 s, et, si le serveur répond quand même 401 (session de la veille, horloge du PC décalée, jeton révoqué), le renouvelle une fois et rejoue la requête ; si le renouvellement est refusé, la session est effacée (l'en-tête repasse à « Compte »). Testé par `check_cloud.tscn`.
- Présence des joueurs (`supabase/migrations/20261013000100_presence.sql`, à appliquer dans le SQL Editor) : table `player_presence` (`last_login`, `last_seen`, `online_until`), sans politique d'accès, mise à jour par la seule fonction `presence_ping('login'|'ping'|'logout')`. `Cloud` (`presence_ping`, `presence_logout`) envoie `login` au premier signal de chaque exécution (connexion, ou relance du jeu avec une session mémorisée), puis `ping` toutes les 60 s ; `logout` à la déconnexion et, au mieux, à la fermeture de la fenêtre. Un joueur est « en ligne » tant que `online_until` (+150 s à chaque signal) est dans le futur : un jeu fermé brutalement repasse hors ligne seul en moins de 3 minutes. `admin_players` et `admin_player_card` renvoient `online`, `last_login` et `last_seen` (liste triée avec les joueurs en ligne d'abord) ; l'onglet Joueurs de l'administration affiche l'état (🟢/⚫) et la dernière connexion, la fiche aussi (plus le dernier signe de vie hors ligne). Test sans réseau : `--script res://tools/check_super_admin.gd`.
- Tests sans réseau : `godot --headless --path . res://tools/check_cloud.tscn` (compte), `res://tools/check_account.tscn` (fenêtre de compte), `res://tools/check_challenges.tscn` (défis, classement, envoi du score) ; suivi d'une vraie partie (affichage ou Xvfb requis) : `--script res://tools/check_run_tracking.gd`.
- Rejeu vérifié (en cours, étapes 1–4 faites) : toute la partie découle d'une graine texte (`Seeds`, `GameRng` : flux nommés combat/loot/trap/wander/village/ids, état sauvegardé avec la partie) et d'une horloge de jeu (`GameClock`, jamais l'heure réelle). Les actions du joueur sont journalisées dans `gs.run_log` (`RunLog`, entrées `[ms, commande, …]`) : déplacements, combat, objets (`Actions`), forge et Maître des Talents (village), et toutes les fenêtres de décision (`Flows` : fontaine, talents, évolution, piège et ses puzzles, boutique, marchand, victoire, village, modificateurs). Toute action non journalisée marque la partie « souillée » (`RunLog.unrecorded`) : elle n'est alors jamais classée. Le rejeu (`scripts/core/replayer.gd`) fait tourner la vraie scène du jeu et y injecte les commandes ; les règles d'acceptation vivent dans la logique partagée, pas dans l'interface. Tests : `check_determinism.tscn`, `check_game_rng.tscn` (valeurs de référence à confirmer sous Windows), `check_clock.gd`, et `xvfb-run -a godot --path . --script res://tools/check_replay.gd -- <graine> <actions> <niveaux>` (un bot joue une vraie partie, puis le journal est rejoué : l'empreinte de l'état doit être identique). Restent : règles des parties classées (ni administration, ni sauvegarde manuelle, ni retour arrière), vérificateur serveur et classement vérifié par mode de jeu.
- Parties classées par difficulté (serveur, étape 6a, pas encore branché à l'interface) : `supabase/migrations/20261010000200_parties_classees.sql` (réglages par difficulté `ranked_modes`, parties `ranked_runs`, fonctions `start_ranked_run` / `submit_ranked_run`, vue `classement_difficulte` vide tant que rien n'est vérifié). Côté jeu : `scripts/core/ranked_run.gd` (configuration partagée avec le vérificateur, démarrage, envoi, classement). Vérificateur : `tools/replay_run.gd` (rejoue un journal) + `tools/verify_runs.py` + workflow `.github/workflows/verify-runs.yml` (toutes les 15 min, secrets `SUPABASE_URL` et `SUPABASE_SECRET_KEY`, chaque partie est rejouée avec les règles de sa version, étiquette `v<version>`). Une partie classée n'accepte ni administration, ni export/import ; sa sauvegarde est à usage unique.
- Hardcore du mois (étape 6b) : `supabase/migrations/20261010000300_hardcore_mensuel_et_recompenses.sql`. Une graine par mois tirée par le serveur à la première partie du mois, difficulté hardcore, UN essai par jour (jour de Paris, consommé au lancement), classement `classement_periode` des parties vérifiées. Récompenses uniquement cosmétiques et de l'expérience : catalogue `badges` (titres, cadres, couleurs de pseudo), `player_badges`, `xp_log` / vue `account_xp` (niveau de compte), `player_cosmetics` + `equip_cosmetics`. Le vérificateur attribue tout (`award_run` après chaque partie vérifiée, `close_due_periods` pour les badges de rang des mois terminés depuis 2 jours), une seule fois. Côté jeu : section « Hardcore du mois » dans la fenêtre des défis du donjon aléatoire (`challenges_modal.gd`), `RankedRun.launch` / `submit` (journal gardé hors ligne puis renvoyé). Écrans : « Mes récompenses » (`rewards_modal.gd` : niveau de compte, collection de badges, équipement du titre, du cadre et de la couleur), « Parties classées » (`ranked_modal.gd` : un classement par difficulté + lancement), plaques de pseudo avec cadre (`cosmetics.gd`), accessibles depuis la fenêtre des défis et le compte. Tests sans réseau : `xvfb-run -a godot --path . --script res://tools/check_ranked_flow.gd` et `check_rewards_ui.gd`.
- Super admin (étape 6c) : `supabase/migrations/20261010000400_super_admin.sql`. Le rôle est une ligne de la table `admins` (aucune politique : illisible et inscriptible depuis le jeu ; on l'accorde par SQL depuis le tableau de bord : `insert into public.admins (player_id) values ('<uuid>')`). Chaque fonction `admin_*` revérifie le rôle côté serveur (`is_super_admin()`, erreur `acces_refuse`) : un jeu modifié n'obtient rien. Parties classées de TEST (`admin_start_ranked_run`, colonne `ranked_runs.test`) : n'utilisent pas l'essai du jour, exclues des classements, de l'XP, des badges et de la clôture des mois, mais rejouées par le vérificateur ; le Hardcore du mois de test garde les réglages du mois avec une graine aléatoire (la vraie graine n'est jamais révélée). Statistiques en lecture seule : `admin_overview`, `admin_players`, `admin_runs` (ni courriels ni journaux d'actions), et `admin_purge_tests`. Côté jeu : bouton « Super admin » dans la fenêtre Compte (affiché seulement si le serveur confirme le rôle), `super_admin.gd` / `super_admin_modal.gd`. Test sans réseau : `xvfb-run -a godot --path . --script res://tools/check_super_admin.gd`.

## Effets de sorts
- L'effet visuel d'un sort est indépendant de son `style` (école : le style décide aussi de la logique de combat, magique ou physique). Trois champs sur le sort : `fx` (identifiant d'effet, `classic` = effet d'origine en sprites, vide = effet par défaut du style), `fxTint` (couleur HTML, vide = couleur d'origine) et `fxPower` (0,6 à 2). `Data.ensure_defaults` les ajoute aux anciens sorts et aux sauvegardes.
- `scripts/dungeon/spell_fx_library.gd` (`SpellFxLibrary`) : catalogue des effets avancés (id, style et mode compatibles, script), teintes et intensités proposées, résolution de l'effet (effet inconnu ou incompatible = effet par défaut du style), palier de qualité, point d'entrée `cast`. `combat.gd` et `main.gd` y passent ; l'effet d'origine reste `SpellFxStyles.cast_spell`. Ajouter un effet = une entrée du catalogue + le script (une classe qui étend `spell_fx_kit.gd` avec une méthode `play(spell_id, target, ctx)`) + les textes `admin.spells.fx_*`. `SPELL_DEFAULT` associe à chaque sort d'origine son effet propre (résolution : effet choisi valide, sinon effet propre du sort, sinon premier effet du catalogue compatible avec le style et le mode, sinon classique).
- `scripts/dungeon/spell_fx_kit.gd` : boîte à outils commune des effets avancés (extraite d'Éclat Arcanique) : shaders (onde de choc face caméra ou à plat, lentille, orbe, rayon, plasma, roche en fusion, flamme et pilier à billboard vertical, trait de lame, dôme hexagonal), bruit de valeur 2D/3D, particules GPU (`_gpu`, `_pmat`, `_pmat_grow`, rubans), lumière dynamique, secousse, décalque générique `_glyph_decal`, et deux « moteurs » pilotés par dictionnaire : `_fly` (projectile : corps plasma, cristal ou maillage, halo, traînées, satellites, lentille, lampe) et `_hit_fx` (impact : éclair, ondes, éclats, rubans, étincelles, fumées additives ou sombres, décalque, lampe, secousse). `_c` fait tourner la palette de l'effet (`_base_hue`) vers la teinte choisie. `scripts/dungeon/spell_glyphs.gd` dessine les motifs gravés au sol (une texture 384 px par motif, en niveaux de gris multipliés par l'opacité).
- `scripts/dungeon/spell_fx_fire.gd` : boule de feu (plasma `SH_PLASMA` à bruit 3D qui défile, traînées de flammes, de fumée et de braises), météore (roche `SH_ROCK` : pierre sombre fendue de crêtes incandescentes, un météore par monstre en diagonale), colonne de feu (trois langues `SH_FLAME` superposées qui jaillissent d'une brûlure gravée au sol, tourbillon de braises en anneau, fumée au sommet, lampe qui gonfle puis s'éteint).
- Écoles : `spell_fx_ice.gd` (javelot, grêle : glaçons en volume et éclats), `spell_fx_holy.gd` (attaques sacrées et soins : piliers, sceaux au sol, lances, hélices de lumière, dôme), `spell_fx_shadow.gd` (sphères de vide, fumée noire, lames, pentagrammes, ciel d'apocalypse), `spell_fx_bard.gd` (notes en volume, portée, harpe, lune de la berceuse), `spell_fx_physical.gd` (coups de lame : traits `SH_STREAK`, étincelles et rubans, éclats de roche, sang, poison ; tirs : flèche en volume qui file ; plus les quatre sorts arcaniques de ralentissement et de flèches). `spell_glyphs.gd` dessine les motifs gravés (brûlure, givre, soleil, jugement, anathème, pentagramme). Chaque effet est une recette courte (`_fly` pour le projectile, `_hit_fx` pour l'impact) ; `SPELL_DEFAULT` associe chaque sort d'origine à son effet, les sorts créés dans l'éditeur reprennent l'effet par défaut de leur école et de leur mode. Noms de méthodes d'un script d'école : ne jamais reprendre celui d'une méthode du parent.
- École de nature : `spell_fx_nature.gd` (feuilles et pétales en textures procédurales, épine et lianes en maillages `SurfaceTool` avec ombrage cuit dans les couleurs de sommets, éclair en segments `_beam` qui se recouvrent, nuée de particules à forte turbulence) ; six sorts dans `data/default_config.json` (`spell_nature1` à `6`, style `nature`, aucun n'est attribué à une classe pour l'instant : les monstres peuvent les tirer comme capacité, le créateur les attribue). Migration des sauvegardes et configurations (schéma 8 → 9, `SaveMigrations._v8_to_v9`) : les sorts du jeu manquants sont ajoutés, sans dupliquer ni écraser un sort existant, sauf dans un donjon personnalisé ; testé par `tools/check_saves.tscn`.
- Capacités des monstres : `combat.gd` (`_monster_use_ability`) ajoute à l'événement `fx3d` un contexte `fromMonster: true` avec `victim` (place du héros visé, 0 à 3) ; `SpellFxLibrary.cast` le route vers `spell_fx_monster.gd` (étend le script de nature pour réutiliser ses briques) : le sort part du monstre (point visé de `CombatStage.target_point`) vers la place du héros (`_slot_pos`). Quatre familles choisies d'après l'effet du sort (`RAIN_FX`, `BURST_FX`, `CLAW_FX`, sinon projectile) et la palette de l'école. Sans rendu avancé (palier 0 ou pas Forward+), seule l'animation du coup reçu joue (l'effet d'origine tire vers les monstres, pas vers le groupe). Les graines de partie d'une version à l'autre ne donnent plus les mêmes donjons : le générateur tire les capacités dans la liste des sorts de dégâts, qui s'est allongée.
- Classe Druide : `class_druid` (base, bâton et masse, sorts nature 1, 5 et 2 aux niveaux 1, 3 et 6) évolue au niveau 5 en `class_warden` (Gardien de la Forêt : soins et protection, sorts aux niveaux 7, 13, 20, 27) ou `class_stormcaller` (Druide de la Tempête : dégâts de zone, mêmes niveaux). Cinq sorts de nature de plus (`spell_nature7` à `11` : écorce protectrice `shieldSingle`, sève régénérante `healSingle`, arbre-monde `healParty`, ouragan de feuilles et colère de la nature `damageGroup`) avec leurs effets (`nature_bark`, `nature_sap`, `nature_worldtree`, `nature_cyclone`, `nature_wrath` : tronc `SurfaceTool` qui pousse, couronne de feuillage persistante `_crown`, couronne de lianes `_vine_ring`). Talents : `data/class_talents.json` (5 paliers de 2 choix par classe). Le nom « Druide » est déclaré partout où existe la liste des classes de base : `AdminUtil.BASE_ARCHETYPES`, `Data.BASE_EVOLUTIONS`, `Saves._base_class`, `IconPicker.PORTRAIT_CLASSES`, `DungeonGenerator.ARCHETYPE_STATS`, `PORTRAIT_COUNTS`, `PORTRAIT_FILES` (une classe oubliée dans l'une de ces listes manque à la génération aléatoire ou aux talents). Icônes : `tools/gen_druid_icons.py` écrit les 3 icônes de classe et les 11 icônes de sorts de nature (`spell_nature1` à `11`, qui remplacent les anciens emoji). Portraits : `druide_0` à `4` sont des copies d'illustrations existantes (cerf feuillu, orc chaman, rôdeuse à capuche de feuilles, guerrière aux peintures vertes, mage de foudre) ; `PORTRAIT_TWINS` empêche de voir la même image deux fois dans un groupe (une classe évoluée reprend le portrait de sa classe de base d'après `evolvesFrom`). Pour de nouveaux visuels, déposer `druide_5.webp`… (128×128) et augmenter `PORTRAIT_COUNTS["Druide"]`. Migration (schéma 9 → 10, `SaveMigrations._v9_to_v10`) : ajoute les trois classes et les sorts manquants (jamais dans un donjon personnalisé, jamais si une classe du créateur porte déjà le même identifiant ou le même nom) et passe les icônes emoji des sorts de nature à l'image seulement si le créateur ne les avait pas changées ; testée par `tools/check_saves.tscn`. Contrôle de la classe : `tools/check_druid.tscn`. Les graines de partie ne redonnent plus les mêmes groupes : le Druide entre dans le tirage des classes de base.
- Paliers (`SpellFxLibrary.tier`, d'après les options graphiques) : 0 sans halo (`fx_glow` désactivé) = effet d'origine ; 1 = particules GPU, halo HDR ; 2 = + lumière dynamique qui éclaire la brume, rune au sol (option `fx_decals`) ; 3 (Ultra, `particles` ≥ 1,25) = + lentille de distorsion. Rendu non Forward+ : effet d'origine. Le script de l'effet est chargé à l'exécution ; s'il ne se charge pas, l'effet d'origine joue à la place.
- `scripts/dungeon/spell_fx_arcane.gd` (palette violette de base tournée par défaut vers le bleu, `DEFAULT_HUE`) : cristal, orbe de mana et rayon (shaders d'onde de choc, de lentille, d'orbe et de rayon ; rubans de particules GPU ; décalque de cercle runique (futhark ancien dessiné par traits dans une texture 512 px, couleur multipliée par l'opacité car l'émission du décalque ignore l'alpha) ; secousse de caméra désactivée par « mouvement réduit »). Le contrat avec le combat est conservé (`SpellFx3D.busy`, `wait_idle`) ; les shaders sont précompilés par `warm_up.gd`.
- Éditeur : colonne « Style (animation) » de l'onglet Sorts (`admin_spells.gd`) avec effet, teinte, intensité et bouton « Aperçu » (`scripts/ui/spell_fx_preview.gd` : petite scène 3D à trois mannequins, avec repères des quatre places du groupe ; le contexte transmis contient les trois cibles, l'allié (place 2) et le lanceur (place 3), si bien que les effets de groupe et de soin sont montrés comme en combat ; effet joué en boucle avec les réglages graphiques actuels).
- Les capacités spéciales des monstres (sorts de dégâts tirés au hasard) ne jouent pas d'effet de sort, seulement l'animation du coup reçu.

## Interface de jeu (colonne de droite et menu du haut)
Écart voulu avec la page d'origine, où le menu « 💾 Sauvegarde » était un panneau en bas de la colonne de droite et le grimoire un petit panneau (2 lignes visibles à 1920×1080).
- Menu du haut : `SaveMenu` (`save_menu.gd`) est hébergé par `AppHeader.add_save_menu` (`app_header.gd`), entre « Paramètres » et « Compte ». Il n'existe qu'en jeu (l'accueil n'en a pas). La liste s'ouvre sous le bouton, large d'au moins 300 px de conception et recadrée dans l'écran ; le groupe de boutons du haut reste déployé tant qu'elle est ouverte (`SaveMenu.is_open`). En combat le bouton est inerte et grisé (`locked`, `GameLayout._process`). Les refus des parties classées (pas de sauvegarde, d'export ni d'import) restent dans `main.gd` (`_on_menu`). Sur mobile (portrait) le bouton n'affiche que l'icône 💾.
- Colonne de droite (`GameLayout._rebuild`, paysage) : Carte, Besace, Grimoire. Le panneau « Menu » n'existe plus (ni son onglet en portrait, qui garde Besace et Journal). La besace garde la taille de son contenu (`SIZE_SHRINK_BEGIN`) et le grimoire prend tout le reste de la colonne (`SIZE_EXPAND_FILL`). La police du journal (`LogPanel`) passe de 14 px à 0,9 rem (≈ 16 px ; 0,8 rem en portrait).
- Carte repliable : bouton ▾/▸ à gauche du titre du panneau (le bouton 🗺️ « plein écran » reste à droite) ; replié, il ne reste que le titre et le grimoire occupe la place libérée. L'état est `GameLayout.map_folded` (variable statique) : il vaut pour la session et ne fait partie ni des sauvegardes ni des configurations, donc aucune migration (le schéma reste 10). Textes : `ui.game_layout.replier_la_carte` et `ui.game_layout.deplier_la_carte`.

## Fenêtre du marchand (`scripts/ui/shop_modal.gd`)
Sélection : chaque carte a une clé (`_gkey`) ; les piles (potions, parchemins identiques) se regroupent par `Inventory.stack_key`, mais un objet non empilable est désigné par son indice dans la besace, car deux exemplaires d'une même définition partagent le même `id` (ancien bug : en vendre un en sélectionnait un autre). Le bouton Acheter/Vendre, avec son prix, est tout en haut de la fiche (sous le titre), suivi du motif de refus, de la quantité (piles) et des caractéristiques. Sélection multiple (onglet Vendre, bouton « ☑ Sélection multiple », ou Ctrl/Maj + clic) : cartes cochées ☐/✓, « Tout sélectionner/désélectionner », total en or, une seule transaction par objet via `Flows.input("shop", …)` (donc journalisée et rejouable) ; les clés sont refusées. État d'interface seulement : aucune migration de sauvegarde (schéma inchangé).

## Deux monstres côte à côte
`Combat.engaged()` engage le premier monstre adjacent dans n'importe quelle direction (le regard d'abord). Quand le premier tombait, le second (sur le côté ou derrière) gardait le combat engagé alors que le groupe regardait ailleurs : fenêtre de combat vide, attaques dans le vide, seule la fuite sortait de là. `CombatController._face_engaged()` tourne maintenant le groupe vers l'adversaire adjacent avant chaque tour (début de `_run_turns`) et après chaque action (`_after_action`), comme `refresh()` le faisait déjà après un déplacement. Aucune donnée sauvegardée : aucune migration. Test : `xvfb-run -a godot --path . --rendering-driver opengl3 --script res://tools/check_double_combat.gd` (monstre devant, monstre derrière : le groupe doit se retourner après la mort du premier).

## Raretés et capacités (`scripts/rules/rarity.gd`)
Six paliers : commun (gris), inhabituel (vert, bonus ×1,15), rare (bleu, ×1,3), épique (violet, ×1,5), légendaire (orange, ×1,7), mythique (rouge, ×2). Un objet porte `rarity` et `perks` : [{id, value}] ; sans `rarity`, il est commun, sauf `legendary: true` (anciens objets et administration) qui le rend légendaire, avec l'ancien couple `legendaryPerk` / `legendaryValue` lu comme capacité (`Rarity.perks_of`) : aucune migration de sauvegarde.
Capacités par palier (`Rarity.POOLS`) : inhabituel, une petite (critique, esquive, or gagné) ; rare, une moyenne (vol de vie, renvoi, dégâts de sort, critique) ; épique, une capacité épique (exécution sous 25 % de PV, poison à chaque coup, dégâts critiques, vol de vie) plus une inhabituelle ; légendaire, une puissante (vol de vie, critique, renvoi, « dernier souffle » : survit à un coup mortel une fois par combat) ; mythique, une légendaire plus une épique, et 2 pièces mythiques portées donnent +10 % critique. Les effets sont appliqués par `Combat` (`_hit_monster`, `_monster_attack_party`, `_handle_death` pour l'or ; `end_combat_reset` recharge « dernier souffle » à la fin du combat), l'esquive par `Characters.recompute`.
Tirage (`Rarity.weights` / `roll`) : selon l'origine (`floor`, `monster`, `boss` rare ou mieux, `reward` salles secrètes, `shop`, `village`, `deal` pour une belle affaire), avec une montée selon le niveau, le numéro de partie et la difficulté (plafonnée). `DungeonGenerator.make_weapon/armor/jewelry` tirent la rareté de chaque objet ; `apply_legendary` fait monter un objet de boss ou de salle secrète au légendaire, et au mythique avec une chance croissante (`mythic_chance`) ; une « pitié » (`_legend_pity`, +8 points par gardien sans légendaire, plafonnée à 40, remise à zéro au légendaire) rapproche le prochain légendaire. Marchands : `Shop._rank_offers` donne une rareté à chaque offre (jamais légendaire) ; une belle affaire est au moins rare ; le prix (`Shop.price`) est multiplié par la rareté (×1,5 / ×2,5 / ×4 / ×7 / ×12).
Interface : nom et liseré colorés (`Rarity.color`), « Rareté · type » (`EquipDock.type_label`), lignes de capacités dans les infobulles, la fiche de l'équipement et la fenêtre du marchand. Administration : éditeur `AdminRarity` (palier puis capacités et valeurs) dans l'onglet Objets et dans les niveaux. Tests : `check_rarity.tscn` (répartition, nombre de capacités, prix, compatibilité) et `xvfb-run -a godot --path . --rendering-driver opengl3 --script res://tools/check_rarity_combat.gd` (infobulles, marchand, dernier souffle).

## Armes de départ par classe
`Characters.SIGNATURE_WEAPON` donne l'arme emblématique de chaque classe (bâton : mage, druide et leurs évolutions ; épée : guerrier, barde, paladin ; arc : archer ; masse : prêtre, clerc ; dague : roublard, voleur, assassin ; hache : berserker, skalde…), lue par `Characters.signature_weapon_type` (repli sur le premier type autorisé si la classe est inconnue ou n'autorise pas ce type). `DungeonGenerator.generate_party` choisit l'arme de départ parmi les armes de ce type dans la bibliothèque (repli sur un type autorisé si la bibliothèque n'en a aucune), et `Characters.start_weapon` utilise la même règle ; avant, le type était tiré au hasard parmi les types autorisés (un mage pouvait commencer avec une dague). Génération seulement : les groupes déjà créés gardent leur équipement, aucune migration. Test : `check_start_weapons.tscn`.

## Clés de porte
La clé d'une porte du donjon (`key_gen_<niveau>`) porte le numéro de son niveau dans son nom (« Clé du niveau 3 », clé de langue `rules.dungeon_generator.cle_du_niveau`), pour savoir où l'utiliser une fois dans la besace. La clé de l'arche (boss) est inchangée. Seules les nouvelles générations changent : les clés des parties en cours gardent leur ancien nom (« Clé trouvée »), aucune migration.

## Marchands : qualité des offres
`Shop.random_offers`, `merchant_offers` et `village_offers` reçoivent le groupe (`gs.party`, passé par `interactions.gd`). Après la génération normale (armes et équipements), `_rank_offers` fait varier chaque offre : ~35 % sont des « belles affaires » et au moins une l'est toujours quand le groupe est connu. Une belle affaire (`upgradeOffer`) est mise à l'échelle (`_scale`, plafond ×12, +1 minimum par bonus) pour dépasser de 25 % à 70 % (au moins +2 de puissance, `Inventory.power`) le meilleur objet porté à son emplacement par un héros (`reference_power`) ; les autres varient de −25 % à +10 % autour de la valeur normale, donc certaines sont plus faibles que le stuff actuel. Le prix suit les bonus (`Shop.price`, ×1,7 au village) : une belle affaire coûte plus cher. Les flèches ▲/▼ de la fenêtre du marchand comparent déjà chaque objet à ce que porte le héros. Tirages sur le flux « loot » ; sans groupe passé en argument, seule la variation s'applique. Offres générées à l'ouverture et non sauvegardées avant : aucune migration (schéma inchangé). Test : `check_merchant_quality.tscn` (belles affaires toujours meilleures que le stuff, variété des puissances).

## Potions (équilibrage)
Valeurs à la génération (`DungeonGenerator`, `Shop`) : au sol, soin `12 + 8 × palier + 2 × bonus de partie`, endurance `18 + 9 × palier + 3 × bonus` (palier = niveau ÷ 3) ; butin des monstres, soin `10 + 4 × niveau + 2 × bonus`, endurance `15 + 5 × niveau + 3 × bonus` ; marchands, soin `16 + 4 × niveau`, endurance `min(60, 12 + 3 × niveau)`. Le prix (`Shop.price`) vaut `3 + 0,4 × (soin + endurance)` : une potion plus forte coûte à peu près le même prix qu'avant. Les objets déjà générés (niveaux d'une partie en cours, sauvegardes, configurations, objets de la bibliothèque de l'administration) gardent leur valeur : seules les nouvelles générations changent, donc aucune migration (schéma inchangé).

## Défi de la semaine « Verre brisé »
Modificateur `mod_glass` (`data/game_constants.json`) : PV max du groupe ×0,5, `critChanceBonus: 5` (critique du groupe +5 points, additionné par `DungeonGenerator.combine_mods`, lu par `Combat` et par la fenêtre du marchand) et `maxGroupSize: 2` (plafond de taille des groupes de monstres, le plus bas des modificateurs actifs l'emporte, 3 par défaut : le tirage `group_size` du générateur est borné, aucun groupe de 3 n'est créé). L'info du défi affichée dans le jeu vient de `descFr/descEn` du modificateur et de `weekly_rules.desc_fr/desc_en` côté serveur (`supabase/migrations/20261013000200_verre_brise.sql`, à appliquer dans le SQL Editor). Les donjons déjà générés (sauvegardes en cours) gardent leurs groupes : le plafond ne joue qu'à la génération, donc aucune migration de sauvegarde (schéma inchangé). Test : `check_weekly.tscn`.

## Parties suspectes : « vues »
`supabase/migrations/20261013000300_parties_suspectes_vues.sql` (à appliquer dans le SQL Editor) : table `suspect_seen` (sans politique d'accès). `admin_suspect_runs` ignore les parties vues, et comme `admin_queue_counts` s'appuie sur elle, le rappel d'ouverture du jeu et le compteur de l'onglet les ignorent aussi. Fonctions réservées aux super admins : `admin_suspect_seen(run)` (une partie), `admin_suspect_clear(jours)` (toute la liste), `admin_suspect_restore()` (tout réafficher), `admin_suspect_seen_count()`, toutes journalisées (`suspect_seen`, `suspect_clear`, `suspect_restore`). Rien n'est supprimé : la partie reste dans les classements et l'historique du joueur ; une nouvelle partie suspecte apparaît normalement. Côté jeu : onglet Suspectes (`super_admin_modal.gd`), bouton « ✔ Vu » par partie, « Tout marquer comme vu » (avec confirmation) et « Réafficher les parties vues (N) ». Pas de donnée locale : aucune migration de sauvegarde. Piège : l'API Supabase charge `pg_safeupdate`, qui refuse tout `DELETE` / `UPDATE` sans `WHERE` dans une fonction appelée depuis le jeu ; « Réafficher » échouait pour cette raison, corrigé par `20261017000100_suspect_restore_fix.sql` (`where true`) — toujours mettre une clause `WHERE` dans les fonctions.

## Parties suspectes : niveaux
`supabase/migrations/20261017000200_suspectes_niveaux.sql` (à appliquer dans le SQL Editor) remplace `admin_suspect_runs` et `admin_queue_counts`. Chaque partie reçoit un niveau : `probable` (récidive, moins de 10 % de la durée médiane, score invraisemblable), `watch` (rejetée non technique, moins de 20 % de la médiane) ou `info` (rejet technique : `version_non_rejouable`, `rejeu_*`, `engagement_inattendu`, `fenetre_absente`, `jeu_jamais_au_repos`, `reinitialise_dev`, `annulee_dev`, qui ne prouvent pas une triche). Médiane sur au moins 10 parties validées de même difficulté et même score ; récidive à 5 rejets non techniques ou plus, appliquée seulement aux parties rejetées ou trop rapides du joueur. Liste triée du plus au moins suspect ; le rappel d'ouverture du jeu ignore le niveau `info`. L'onglet Suspectes (`super_admin_modal.gd`) colore le titre et affiche le niveau.

### Compteur de performances
`scripts/core/perf_overlay.gd` : un seul `Label` (couche 120) en haut à gauche, sans panneau ni cadre ; lisibilité assurée par un liseré de texte sombre. Une ligne : images/s, RAM, VRAM, appels de dessin (couleur selon les images/s). F3 ou bouton 📊.
Taille constante : la ligne est compensée par le rapport entre l'échelle de la scène de jeu (zone de conception 1600 x 1000) et l'échelle courante (`content_scale_factor`), donc elle garde la taille qu'elle a dans le donjon au lancement et dans le menu d'accueil.

## Pièges : pointes au sol
`scripts/dungeon/trap_spikes.gd` (`TrapSpikes`) : le piège `spikes` est un vrai volume, plus un décalque. Un maillage unique (`ArrayMesh`, construit par `SurfaceTool` puis partagé par tous les pièges) : surface 0 = plaque de fer biseautée, rivets et douilles (normales explicites) ; surface 1 = 25 pointes d'acier à trois anneaux (hauteurs et inclinaisons variées, dégradé rouille → acier, quelques-unes tachées de sang), normales lissées. Elles projettent des ombres sous la lumière des torches. Une ombre de contact douce (texture générée) noircit le sol autour. `TrapDecals.make_mesh("spikes")` y renvoie ; la vapeur, les fléchettes, la fosse et la rune ont leur propre modèle (sections suivantes) : plus aucun piège n'est un décalque.
Les pointes forment un nœud enfant `Spikes` : quand le piège est désamorcé (`Interactions._trap_resolved`), `EntityLayer.disarm_item` appelle `TrapSpikes.retract` (écrasement progressif en 0,5 s dans la plaque, qui reste en place) ; au chargement d'un niveau (`main.gd`), l'état « désamorcé » des sauvegardes rentre les pointes tout de suite, sans animation, donc rien à migrer. Les autres pièges disparaissent comme avant.

## Pièges : vapeur verte
`scripts/dungeon/trap_gas.gd` (`TrapGas`) : bouche d'aération de fer (maillage `SurfaceTool`, mêmes briques `TrapSpikes.add_box` / `add_prism`) et nuage vert épais en continu : trois émetteurs `GPUParticles3D` (colonne de volutes, nappe rasante qui coule sur le sol, cœur lumineux additif en HDR pour le halo de l'environnement), turbulence, bouffées en texture de nuage générée (bruit simplex), `proximity_fade` (Forward+) pour estomper les bouffées au contact du sol et des murs ; lueur verte pulsante (`OmniLight3D`, sans composante spéculaire : sur un sol mouillé elle dessinait une traînée verte brillante sous la bouche) et brume volumétrique verte (`FogVolume`, Forward+ uniquement). Le nombre de particules suit l'option `particles`. Les particules sont préchauffées (`preprocess`) : le nuage est déjà formé à l'apparition. `TrapGas.stop` (piège désamorcé, `EntityLayer.disarm_item`) coupe les émetteurs, éteint la lueur et dissipe la brume en quelques secondes ; au chargement d'un niveau déjà désamorcé, le nuage n'est pas créé. `warm_up.gd` précompile les deux pièges.

### Sons des pièges qui se déclenchent
Un son propre à chaque type de piège, joué seulement quand le piège se déclenche pour de bon, c'est-à-dire quand la dernière tentative échoue (jet raté d'une méthode qui résout le piège, échec simple ou critique, ou puzzle raté) : `Sound.TRAP_FAIL_SOUNDS` (`spikes` → `trap_snap.ogg`, `gas` → `steam_hiss.ogg`, `dart` → `dart_swish.ogg`, `pit` → `wood_thud.ogg`, `rune` → `rune_seal.ogg`) ; un type sans son attitré joue le coup habituel (`hit`). `Sound.trap_fail(kind)` est appelé par `TrapModal._roll_outcome` avec le type du piège ; un jet de sonde raté, lui, ne déclenche rien et laisse un nouveau choix : il ne joue pas ce son (`TrapModal._roll_outcome` ignore la sonde). Chaque fichier est converti du MP3 fourni en OGG et atténué à l'export pour atteindre -20 LUFS (comme `dice.ogg`), avec un gain `SFX_GAIN_DB` de -14 (même méthode que tous les effets : cible -34 LUFS, `tools/sfx_levels.py`). Règle pour tout nouveau son : le mesurer avec `tools/sfx_levels.py` et reporter son gain dans `SFX_GAIN_DB`.

Casse-têtes de piège (`scripts/ui/trap_puzzle_*.gd`, base `TrapPuzzle`). **Énigmes** : `TrapPuzzleRiddle.COUNT` (120) énigmes, chacune = 5 clés de langue `ui.trap_puzzle.riddle_<n>_{q,a,b,c,d}` (question, bonne réponse en `a`, trois leurres ; les réponses sont mélangées à l'affichage) ; l'ordre des numéros est mélangé par le flux `trap` de `GameRng` (rejeu identique) et chaque fenêtre ne repose jamais deux fois la même. Pour en ajouter : augmenter `COUNT` et créer les cinq clés FR et EN ; `tools/check_lang.py` vérifie qu'aucune énigme n'est incomplète ni à réponses en double. **Cordes** (`TrapPuzzleWires`) : même règle de jeu que les fils (`TrapRules.make_wires`, un seul coup de cisaille), dessin en cordes torsadées — `_dense` (un point tous les ~3 px), `_build` (traits obliques clairs/sombres régulièrement espacés = torons, quelques fibres), `_draw_rope` (ombre, âme sombre, fût coloré, torons, reflet), `_draw_ferrule` (bagues de laiton aux deux bouts) ; l'épaisseur (`_hw`) et l'ondulation s'adaptent à l'écart entre cordes (3 à 6 cordes) pour qu'elles ne se chevauchent jamais. La géométrie est calculée une fois (`begin`), une corde coupée calcule ses deux moitiés pendantes et ses bouts effilochés (`_make_halves`) au moment du coup de cisaille. Contrôle visuel : `shot_game.gd` (`steps=trapui kind=spikes methods=disarm puzzle=wires "acts=click:Trancher;wait:3;solve:bad;shot:b"`).

Fin de combat : quand le dernier monstre meurt, `CombatController` (événement `monster_died`) garde la salle de combat affichée pendant son animation d'effondrement (`DEATH_ANIM_SEC`, 0,65 s, via `_draining` : `in_combat()` reste vrai et la partie n'est pas « au repos » pour les parties classées), puis émet `changed` pour que `Main._sync_stage` referme la salle, et seulement alors lance l'écran de victoire. Sans animation de monstres (réglage), aucune attente. Contrôle visuel : `tools/shot_death.gd` (monstre à 1 PV, images pendant et après la mort). Les chiffres, la réaction et la mort d'un monstre s'appliquent à l'**impact** du sort et non à la fin de son fondu : `CombatController._drain` attend `SpellFx3D.wait_hit` (un effet est « touché » quand tous ses projectiles `_fly` / `_projectile` sont arrivés, ou, sans projectile, quand son premier impact différé `_later` a joué, au plus tard `SpellFx3D.HIT_CAP` = 0,35 s après son départ) ; les actions suivantes et l'écran de victoire attendent toujours la fin complète de l'effet (`busy` / `wait_idle`). `tools/shot_death.tscn` mesure le délai coup → effondrement.

Micro-saccade à l'entrée en rage : deux causes corrigées. (1) `CombatStage._make_rage_aura` créait un `Shader.new()` par monstre : le shader chauffé au chargement n'était donc pas celui du combat, et le moteur recompilait à chaque première rage ; le shader est maintenant unique (`CombatStage._rage_shader()`, comme `StatusAura._fire_shader` et `SpellFxKit._shader`). Règle : tout shader utilisé par un effet de jeu est créé une seule fois (variable statique), jamais à l'apparition de l'effet. (2) Le préchauffage (`WarmUp.run`) tournait en MSAA désactivé et sans les effets d'environnement (occlusion ambiante, halo, étalonnage) alors que la vue de jeu les utilise : le moteur compile un pipeline par format d'image, donc le premier affichage de chaque effet recompilait en plein jeu. Le préchauffage reprend maintenant `Settings.msaa_mode()` et `VisualFx.apply_environment`. Les saccades de compilation ne se mesurent pas sans carte graphique (le rendu logiciel de `xvfb` est trop lent), `tools/check_rage_hitch.tscn` sert à les mesurer sur une vraie machine (`WARM=1` pour comparer avec le préchauffage).

Pied de page du jeu (`GameLayout.footer`, un `VBoxContainer`) : la ligne de version est un simple texte, et seul le bouton « Made by Claude & Nydaunvan » (aussi large que son texte) ouvre la page de remerciements ; test `tools/check_credits_click.tscn` (clic loin du texte, sur la version, puis sur le bouton). La musique du générique passe par un bus propre `MusicDry` (`Sound._bus_dry`, sans réverbération, même volume que `Music`), pour ne pas avoir l'écho du bus `Music`.

Piège GDScript : une fonction anonyme qui doit se rappeler elle-même (rafraîchir une liste après un clic) ne peut pas utiliser sa propre variable (`var f := Callable(); f = func(): … f.call()`) : les variables locales sont capturées par copie à la création, donc `f` y est vide et l'appel échoue sans bruit. On passe par un dictionnaire (`var rf := {}; rf["f"] = func(): … rf.f.call()`), partagé par référence. Corrigé dans la fenêtre des emplacements de sauvegarde (la liste restait « vide » après « Sauver ici » jusqu'à la réouverture ; même défaut pour la suppression), la forge, le Maître des Talents et le sélecteur d'icônes. Tests : `tools/check_slot_roundtrip.tscn` (écriture puis relecture d'un emplacement) et `tools/check_slots_ui.tscn` (la liste se rafraîchit après une sauvegarde).

Parcours des récompenses (onglet « Récompenses » du hub en ligne, `online_hub.gd`, `_rw_render`) : les récompenses déjà obtenues par le joueur sont listées en premier, puis celles à obtenir ; dans chaque groupe, par rareté croissante, puis dans l'ordre du catalogue.

Brume en combat (`fog_mist.gd`) : dans les niveaux à brouillard, la brume volumétrique et le brouillard général se dissipent pendant un combat (il reste 15 % de la brume volumétrique et 25 % du brouillard général, `COMBAT_VOLUME` / `COMBAT_GENERAL`) puis reviennent à la fin, en fondu d'environ 1,7 s. `main.gd` fournit `combat_probe` (combat à l'écran : `level_node.stage.active`). Effet purement visuel ; en exploration le facteur vaut 1, rien ne change.

Piège de vapeur permanent : une réussite le désamorce (la vapeur cesse, la dalle reste) ; un échec laisse le nuage en place, le groupe peut avancer, mais s'il repasse sur la dalle un nouveau défi se déclenche (même mécanique que les pointes : `permanent`, `Interactions._apply_trap_hits`). Le générateur et le donjon d'origine créent la vapeur avec `permanent: true`. Migration des sauvegardes et configurations (schéma 3 → 4, `SaveMigrations._v3_to_v4`) : les pièges de vapeur existants (niveaux et bibliothèque) deviennent permanents, une seule fois ; testé par `tools/check_saves.tscn`.

Commandes en attente (parties classées, `main.gd`) : une commande n'est acceptée qu'au repos (`settled()`), donc pendant un effet en cours (fontaine, coup…) un déplacement ou un quart de tour était perdu : il fallait appuyer deux fois. Désormais la dernière commande de déplacement est gardée trois secondes (`PENDING_MS`) et exécutée dès que le jeu est au repos ; elle est journalisée à ce moment-là, comme si le joueur appuyait à cet instant, donc le rejeu reste identique (`check_determinism`, `check_replay` OK).

Personnage à terre (PV à 0) : son portrait passe en niveaux de gris, anneau compris (`UiTheme.circle_gray_material`, paramètre `gray` de `UiTheme.portrait` et de `EquipDock._round_medal`) dans la rangée de portraits en haut de l'équipement, au centre de l'équipement et dans la fiche du personnage (`PartyModal`).
La brume se dissipe de la même façon quand le groupe est à deux cases ou moins du marchand ambulant (distance de Manhattan, y compris debout devant son étal dans la niche) : même facteur et même fondu que pendant un combat, retour à la normale en s'éloignant.

Icônes de classes : chaque classe fournie par le jeu doit avoir une icône en image (`@icon:…`). Les anciennes configurations et sauvegardes avaient parfois un emoji ou une icône introuvable sur des classes évoluées (le choix d'évolution n'affichait alors rien, ex. le Voleur). `SaveMigrations.repair_class_icons` redonne l'icône du jeu à ces classes ; elle est appliquée par la migration v4 → v5 (classes, héros qui portaient l'ancienne icône de leur classe, héros de la sauvegarde) et à chaque chargement de configuration (`Data.ensure_defaults`). Les classes créées par le joueur et les icônes de héros choisies à la main ne sont jamais touchées. Dans l'éditeur, une nouvelle classe reçoit une icône en image (bouclier, ou celle de la classe dont elle dépend pour une évolution) au lieu d'un emoji. Testé par `tools/check_saves.tscn`.

## Pièges : fléchettes murales
`scripts/dungeon/trap_dart.gd` (`TrapDart`) : le piège `dart` est un mécanisme fixé au mur, plus un décalque. `EntityLayer.populate` choisit le mur voisin de la dalle du piège (`LevelBuilder.dart_wall_dir` : jamais un mur évidé par une niche de fontaine ou de marchand, ni un creux voisin ; stable d'après l'identifiant ; `LevelBuilder.niche_data` partage ce calcul avec la construction du niveau) et y pose le modèle, orienté par `TrapDart.yaw_for`. Les torches sont au centre des pans de mur des cases où x + y est pair, à 2,48 m : sur ces cases la plaque est posée plus bas (`LevelBuilder.dart_height`, 1,15 m au lieu de 1,5 m) pour ne pas la chevaucher, et la dalle reste au sol quelle que soit la hauteur (nœud `Slab` à part) ; un piège à fléchettes ne peut exister que contre un mur : `DungeonGenerator.build_config` ne le pose que sur une case adossée à un mur (jamais à une intersection ; à défaut, des pointes) et `EntityLayer.populate` transforme en pointes (`trapKind: spikes`) tout piège à fléchettes d'un niveau existant (donjon personnalisé, sauvegarde) dont la case n'a aucun mur utilisable ou qui est en plein air. Vérifié sur 25 donjons générés (53 pièges à fléchettes, tous contre un mur). Repère local : l'origine est sur le mur, +Z va vers le couloir. Un maillage partagé (`SurfaceTool`, briques `TrapSpikes.add_box`) : encadrement de pierre, tôle de fer rivetée, huit trous cerclés (2 × 4) et la dalle de déclenchement au sol, sur la case du piège ; huit fléchettes (hampe de bois, pointe d'acier, empennage rouge) forment un nœud à part `Darts`. Le piège est proposé quand le groupe arrive sur la dalle (déclenchement habituel d'un piège sur sa case). Piège permanent (`permanent: true`) : une réussite le désamorce (`TrapDart.retract` : les fléchettes rentrent, les trous restent vides, la plaque reste au mur) ; un échec tire une salve (`EntityLayer.fire_item`, appelé par `Interactions._apply_trap_hits` : volée qui traverse le couloir en 0,2 s, puis rechargement) et le piège reste actif pour un nouvel essai si le groupe repasse sur la dalle. Au chargement d'un niveau déjà désamorcé, les fléchettes ne sont pas affichées. Le son de l'échec est `dart_swish.ogg` (converti du MP3 fourni, gain `SFX_GAIN_DB` -13,5 mesuré par `tools/sfx_levels.py`, cible -34 LUFS). Migration des sauvegardes et configurations (schéma 5 → 6, `SaveMigrations._v5_to_v6`, qui partage `_make_permanent` avec la vapeur) : les pièges à fléchettes existants (niveaux et bibliothèque) deviennent permanents ; testé par `tools/check_saves.tscn`. `warm_up.gd` précompile le modèle.

## Pièges : fosse béante
`scripts/dungeon/trap_pit.gd` (`TrapPit`) : le piège `pit` est un vrai trou dans le sol, en haute définition. `LevelBuilder.build` repère les cases portant une fosse (`pits`) et `LevelBuilder._floor_cell` y découpe le sol en quatre bandes autour d'un trou carré de `TrapPit.HALF` (0,85 m) de demi-côté (mêmes UV que le sol plein, valable aussi pour les chemins en plein air). Le nœud du piège (`TrapPit.make(theme)`, posé au niveau du sol au centre de la case) contient un maillage à quatre surfaces : (0) parois maçonnées en assises de blocs taillés sur un fond de mortier sombre (hauteurs et largeurs variées, joints décalés, face avant en retrait irrégulier et quatre chanfreins par bloc, plus sombre en descendant) ; (1) rochers : cubes subdivisés ramenés sur une sphère et déformés par du bruit, posés au sol, normales lissées ; (2) margelle de dalles ébréchées (deux couches : le dessus en retrait fait le biseau) ; (3) pieux du fond (`TrapSpikes._spike`, acier du piège de pointes). Le hasard est à graine fixe : toutes les fosses sont identiques. **Matériaux du thème** : `TrapPit._stone` copie les matériaux mur et sol de `ThemeMaterials.for_theme` du niveau en cours (couleur, normales, occlusion et rugosité pour la pierre ; pixel-art pour damp, lava et temple), les projette en triplanaire (le maillage n'a pas d'UV ; échelle déduite de celle du thème), coupe le relief par parallaxe et laisse les couleurs de sommet assombrir la profondeur : les parois et blocs prennent le mur, la margelle et les rochers le sol, la fosse se fond donc dans le couloir. Une faible `OmniLight3D` froide au fond (`Depth`) évite que l'ombre du bord noie la fosse. Planches (`Planks`, cachées tant que le piège est actif) : cinq planches à arête chanfreinée, deux traverses, deux sangles et des clous de fer ; bois texturé (veinage, cernes, pores, nœuds) en couleur et normales 1024 x 1024 (`assets/misc/pit_wood_albedo.jpg` et `pit_wood_normal.png`, fabriquées par `tools/make_pit_wood.gd` ; relancer ce script pour les régénérer). Piège permanent (`permanent: true`) : une réussite le désamorce (`TrapPit.cover`, appelé par `EntityLayer.disarm_item` : les planches tombent en travers du trou, la lueur du fond est retirée, immédiat au chargement d'un niveau déjà désamorcé) ; un échec laisse la fosse ouverte et le groupe peut avancer, mais s'il repasse sur la case un nouveau défi se déclenche. Le son de l'échec est `wood_thud.ogg` (converti du MP3 fourni, rehaussé de 8 dB avec limiteur car la source est faible, gain `SFX_GAIN_DB` -13,5, cible -34 LUFS). Migration des sauvegardes (schéma 6 → 7, `SaveMigrations._v6_to_v7`, via `_make_permanent`) : les fosses existantes (niveaux et bibliothèque) deviennent permanentes ; testé par `tools/check_saves.tscn`. `warm_up.gd` précompile le modèle (la fosse du mini-niveau passe par `EntityLayer`).

## Pièges : rune de flammes
`scripts/dungeon/trap_rune.gd` (`TrapRune`) : le piège `rune` est le dessin du cercle magique du sort Éclat Arcanique (`SpellFxArcane._rune_tex`, texture partagée et mise en cache : anneaux, 24 runes du futhark, hexagramme) posé à plat sur un plan additif, teinté orange en HDR (elle nourrit le halo de l'environnement) et pulsant en boucle (tween sur la couleur et sur la lueur). Autour : une trace de brûlure sombre sous le dessin, un halo orangé au ras du sol, des braises qui montent le long des anneaux (`GPUParticles3D` en anneau, nombre suivant l'option `particles`) et une `OmniLight3D` orangée sans spéculaire. `TrapRune.fire` (échec du jet, appelé par `EntityLayer.fire_item`) lance une gerbe de flammes (`GPUParticles3D` à tir unique, additives, bouffées `TrapGas._puff_tex`), un éclair de lumière et une surbrillance des runes, puis le cercle se rallume. `TrapRune.stop` (piège désamorcé, `EntityLayer.disarm_item`) coupe la pulsation et toute gerbe en cours (sans quoi elle rallumerait les runes), éteint les runes (elles restent gravées, sombres), les braises, le halo et la lueur ; immédiat au chargement d'un niveau déjà désamorcé. Piège permanent : un échec laisse le piège actif (même mécanique que les pointes). Le son de l'échec est `rune_seal.ogg` (converti du MP3 fourni, gain `SFX_GAIN_DB` -13, cible -34 LUFS). Migration des sauvegardes (schéma 7 → 8, `SaveMigrations._v7_to_v8`, via `_make_permanent`) : les pièges à runes existants (niveaux et bibliothèque) deviennent permanents ; testé par `tools/check_saves.tscn`. Présence dans tous les types de donjon : le générateur (donjons aléatoires et création) tire la rune parmi `TRAP_KINDS`, et le donjon d'origine (`data/default_config.json`) reçoit deux runes et trois fosses (trap6 à trap10, permanentes) en plus de ses pointes, fléchettes et vapeur. Les parties déjà commencées gardent leurs niveaux tels quels (seule la permanence des pièges existants est migrée) ; les nouveaux pièges du donjon d'origine apparaissent dans les nouvelles parties. `warm_up.gd` précompile les quatre modèles.

## Effets de sorts sur les cartes du groupe (essai)

- `CardFxOverlay` (scripts/ui/card_fx_overlay.gd) : couche plein écran au-dessus de l'interface (SubViewport transparent, monde 3D et caméra propres, mise à jour coupée quand aucun effet ne joue). Ajoutée par `Main` juste après la mise en page.
- Sont joués dans la couche : TOUS les sorts et capacités (héros et monstres). Un sort de héros part de la carte du lanceur (`SpellFx3D._start_point`, `caster_idx`) vers le monstre ; un soin ou une protection arrive sur la carte visée ; une capacité de monstre part du monstre vers la carte de la victime. Le coup d'un monstre (événement `fx` « hit » avec `char`, signal `CombatController.fx_hit`) frappe la carte du héros touché (`SpellFxStyles._party_hit`, `victim_idx`). La fontaine (action `fountain`) soigne chaque carte. Les effets de groupe (soin collectif, sanctuaire, hymnes) parcourent `SpellFxStyles._party_slots()` (une place par carte réelle, jamais de doublon) et se centrent via `_party_ends()`. L'attaque normale d'un héros reste dans la vue, sur le monstre, SAUF la flèche de l'archer (action `bow`, événement `fx` avec `char`, signal `fx_attack`) qui part du centre de sa carte (`Main._on_fx_attack`). Les décalages latéraux du départ (`_side`) sont supprimés quand l'effet part d'une carte.
- Placement : la caméra de la couche a le même nombre de pixels par unité de monde que celle de la vue (`tan(fov_couche/2) = tan(fov_vue/2) × hauteur couche / hauteur vue`) ; le point de départ d'un monstre est reprojeté (`_remap`) à l'écran et à la même profondeur. Les places des héros viennent de `PartyHud.card_centers()` et du contexte `slotPx` ; `SpellFx3D.apply_party_ctx` les range dans l'instance de l'effet, `_slot_pos` les utilise.
- Option `card_fx` (Options > jeu, défaut activée, `user://settings.cfg` section `game`, clé absente = activée : aucune migration). Rendu avancé (Forward+) uniquement ; sinon, ou si le placement échoue, l'effet joue dans la vue comme avant.
- Contrôle : `tools/check_card_fx.tscn`.

## Qualité en toutes lettres

Toute description d'arme, d'armure ou de bijou indique sa qualité par un mot (« Commun », « Rare »…), pas seulement par la couleur : ligne de type des infobulles (`EquipDock.type_label`), fiche du marchand (`ShopModal`) et liste d'équipement de la fiche de survol d'un héros (`PartyTip`).

Départ des effets : le point de départ d'un sort de héros est le milieu du bord bas de sa carte (`PartyHud.card_bottoms()`, contexte `slotStartPx`, `SpellFx3D._caster_anchor`) ; les arrivées (cible, soin) visent le centre de la carte (`card_centers()`, `slotPx`). Les ancres « bas de l'écran » des sorts de zone, de sommeil, du cri de guerre et des sorts sacrés ou d'ombre passent aussi par `_caster_anchor`.

Garde-fou des textes d'objets : `tools/check_item_labels.tscn` vérifie qu'aucune ligne de type d'objet (emplacements, types, raretés, deux langues) ne montre une clé de langue brute. Cause du bug « ui.equip_dock.bottes » : `EquipDock._base_type_label` renvoyait le libellé de `SLOT_DEFS` sans le traduire.

- Correctif : `CardFxOverlay.usable()` ne dépend plus ni du rendu (Forward+ / compatibilité) ni du palier d'effets (halo désactivé = palier 0) : sans cela, tous les sorts (archer, druide…) partaient du bas de l'écran. Contrôle : `tools/check_start_all.tscn` (rendu de compatibilité et palier 0 simulés ; départ au bord bas de la carte).

- Profondeur de départ : un effet qui part d'une carte naît à la profondeur du monstre visé (`startDepth`, `SpellFx3D._start_point`), pas à 0,6 devant la caméra : à cette distance, une flèche ou un éclat allongé traversait le plan de la caméra et se dessinait comme un faisceau géant venu du coin de l'écran. Les flèches sont en plus raccourcies (`_tail_k`) dans ce mode. Contrôle visuel : `tools/shot_card_fx.tscn` (rendu réel sous xvfb).

## Écran de chargement fluide

- `LoadingScreen._advance` : la barre (donc l'épée) avance à vitesse progressive (accélération limitée, `ACCEL`), rattrape l'avancement réel sans à-coup, et continue de ramper (`CREEP`) jusqu'à `LEAD` devant lui pendant une longue étape, sans jamais reculer ni dépasser 98,5 % avant la fin réelle.
- Les animations (`SwordBar`, sceau) bornent le pas de temps à 50 ms : une image longue ne fait pas sauter l'aura.
- `Loader._slice` et `Sound` rendent la main toutes les ~5 ms (au lieu de 7-8) ; `Loader._wait_full` laisse la barre finir de se remplir avant de lever le rideau.
- Aucun gros bloc sur le fil principal (l'animation interne de l'épée tourne sur ce fil) : images et scripts sont chargés par `ResourceLoader.load_threaded_request` (`Loader._load_threaded`, fenêtre de 4 à 6 requêtes, sondage à chaque image) ; les sons sont synthétisés dans une seule tâche `WorkerThreadPool` (`Sound.preload_all`, progression pondérée) ; les textures procédurales d'effets sont fabriquées d'avance, une par image (`WarmUp.pregen_effect_resources`), sauf la grande texture de runes (512², calcul pur) qui part sur un fil de travail. Les autres fabriques ne doivent PAS passer sur un fil (erreurs de texte, plantage).
- Mesure : images les plus longues ≤ 20 ms en chargement ; restent le décor (1 image ~130 ms) et la compilation des shaders par le GPU pendant la préparation des effets.
- Shader de l'épée : le bruit est calculé en pixels d'écran (cellules carrées, interpolation quintique, hachage sans motif) pour supprimer les bandes verticales dans l'aura et sur la lame.
- L'aura échantillonne la forme de la lame avec son reflet haut/bas (`sym`) : même luminosité au-dessus et en dessous.
- Contrôle : `tools/check_loading_bar.tscn`.


## Arrivée dans un niveau : jamais d'attaque au pop du joueur

- Génération : aucun monstre à moins de `DungeonGenerator.START_CLEAR` (8) cases du départ ni de l'escalier de retour (la distance n'est réduite que si le niveau n'offre rien d'autre, jamais sous 3) ; un boss reste à 6 cases au moins du départ.
- Exécution : `Wanderers.bind_level` pose `calmTicks = ARRIVAL_CALM_TICKS` (24 pas de 0,5 s = 12 s), le même répit qu'après un combat : aucun monstre ne poursuit le joueur ni ne s'approche de lui. Valable aussi à la reprise d'une sauvegarde.
- Contrôle : `tools/check_start_calm.tscn`. Attention : ces règles changent les donjons tirés d'une graine et les pas de monstres ; le vérificateur de parties classées doit rejouer chaque partie avec les règles de sa version.

## Rage des monstres

- Tout monstre peut avoir une rage : `enrageThreshold` (> 0 : % de PV sous lequel elle se déclenche, 0 = aucune) et `enrageBonusPct` (bonus de dégâts, 30 par défaut). Elle se déclenche dans `Combat` (plus réservée aux boss) ; l'état `enraged` est celui du monstre (ou du groupe).
- Donjons générés : chaque monstre ordinaire a `monsterRageChancePct` % de chance (25 par défaut) d'en avoir une (seuil 30-50 %, bonus 15-30 %) ; les boss en ont toujours une (seuil 35-55 %, bonus 25-40 %) sauf si `bossRage` est faux. Ces deux réglages sont dans l'admin, onglet Général, panneau « Rage des monstres ».
- Admin des niveaux : colonne « Rage » (case + seuil + bonus) ; cocher « Boss » active la rage par défaut (décochable).
- Affichage : halo rouge sombre qui pulse derrière le monstre (`CombatStage._make_rage_halo`, distinct du halo de sélection de groupe), bandeau de combat « en rage : +X % de dégâts », fiche du monstre (seuil, bonus, état).
- Migration de sauvegarde v10 → v11 : le seuil des monstres ordinaires (jusque-là ignoré) est remis à 0 pour garder le comportement des niveaux existants. Contrôles : `tools/check_rage.tscn`, `tools/shot_rage.tscn` (rendu réel).

### Effets de statut persistants
`StatusAura` (scripts/dungeon/status_aura.gd) dessine, avec quelques sprites face caméra animés par le temps, l'aspect de chaque statut actif (`Statuses.active`) : sommeil, étourdissement, poison, brûlure, gel, ralentissement, affaiblissement, cri de guerre, célérité, vigueur, arme enflammée, drain de vie. Un statut peut porter un `look` (la berceuse met `statusLook = "sleep"` : même étourdissement, mais « Z » et libellé « Sommeil »). Monstres : `CombatStage._sync_auras` (toutes les 0,3 s) attache un `StatusAura` au sprite du monstre. Héros : `CardFxOverlay.status_source` (fourni par `Main._hero_status_entries`, rectangles via `PartyHud.card_rects()`) pose un `StatusAura` par carte dans la couche transparente (mélange normal, `mix_mode`) ; la couche reste active tant qu'un statut est affiché. Les boss ont toujours une capacité (`abilitySpellId`). Vérification : `tools/shot_status.tscn` (rendu réel).

`_v11_to_v12` (SaveMigrations) applique les nouvelles valeurs des 6 sorts de dégâts de nature (`DRUID_OLD` → `DRUID_NEW`) aux configurations enregistrées, seulement si les dégâts min/max sont encore ceux d'origine.

### Mort individuelle des membres d'un groupe
Quand un membre d'un groupe tombe sans que le groupe soit anéanti, `CombatStage._refresh_monsters` libère son sprite avec l'animation de mort (`_free_entry(k, true)` → `EntityLayer.die_node` : il s'affaisse et s'efface en 0,5 s) au lieu de le retirer d'un coup ; seul le dernier membre déclenchait jusque-là cette animation (événement `monster_died` → `die_all`). Les survivants glissent vers leur nouvelle place (`slide`, lissage exponentiel dans `_process`) plutôt que de sauter. Le rafraîchissement a lieu après l'impact du coup (`_drain` attend `SpellFx3D.wait_hit`), donc le membre tombe quand le coup le touche. Test : `tools/shot_group_death.tscn`.

### Les monstres ne franchissent pas les pièges actifs
`Wanderers._free` refuse toute case portant un piège encore actif (ni désamorcé, ni pris, ni caché : même condition que le déclenchement sous les pas du joueur, `Interactions.step_items`), pour la poursuite comme pour la patrouille ; la zone de garde n'y change rien. L'état est relu à chaque pas (un piège désamorcé redevient franchissable). Lecture seule de `level_states` pour ne pas créer d'entrée d'état. Test : `tools/check_monster_trap.tscn`.

### Instinct de survie
`Combat._offer_instinct` intercepte un coup direct de monstre (`_monster_attack_party`, `_monster_use_ability`) qui ferait passer un héros de >0 à 0 PV (hors pièges, DoT, héros étourdi/gelé/endormi, une fois par héros et par combat via `instinctUsed`). Le coup est mis en attente (`pending_instinct`, suite `cont`) et l'événement `instinct` est émis ; `CombatController._drain` l'attend (`_await_instinct`, signal `instinct_prompt` → `InstinctOverlay`, minuterie de sécurité) puis appelle `Combat.resolve_instinct(quality)`. Le dé utilise `GameRng.f("combat")` : base par difficulté + bonus de qualité (tiers de la fenêtre : <0,35 tôt, <0,67 bon, sinon parfait) + Constitution, malus de surcoup et de boss enragé, bornes plafond/plancher. Succès : 1 PV (ok) ou 15 % des PV max + effet de classe (`_instinct_class_effect`, famille via `evolvesFrom`), puis statut `slow` 2 tours. Rejeu : l'appui est journalisé (`RunLog.rec("ins", quality)`), `Replayer` attend `ctrl.instinct_waiting`. En partie classée, `RunLog.ranked()` impose la fenêtre standard et ignore les réglages locaux (`Settings.instinct_mode`, `instinct_scale`). Test : `tools/check_instinct.tscn`.

### Régénération en exploration (second souffle)
`ExploreRegen.on_step` (appelée par `Interactions.step_stamina` après chaque pas) compte les pas sur des cases absentes des 4 dernières (`regenTrail`) ; tous les N pas (`STEPS` : 6 / 8 / 12 / 20 selon la difficulté) chaque héros vivant, ni empoisonné ni brûlé, regagne 1 % de ses PV max (min. 1, ×1,25 pour la famille Prêtre/Druide, +0,1 % par point de Constitution au-dessus de 10) jusqu'à 60 % des PV max. Aucun gain en combat ni pendant `regenCooldown` (2 pas, posé par `CombatController` à la fin d'un combat). Fondée sur les pas, pas sur le temps : déterministe en rejeu et en partie classée. Option `staminaSettings.exploreRegen` (Admin › Général). Test : `tools/check_regen.tscn`.

### Mort d'un monstre : après la fin de l'effet
Dans `CombatController._drain`, les chiffres et la réaction (`mon_hit`) restent calés sur l'impact du sort (`SpellFx3D.wait_hit`), mais l'événement `monster_died` attend `SpellFx3D.wait_idle` avant de lancer l'animation de mort (`remove_monster`, ou la chute du membre de groupe via le `changed` qui suit) : elle part donc à la fin de l'effet, quelle que soit sa durée. Signal de test `monster_death_started` ; test : `tools/check_death_timing.tscn` (mort mesurée à 1 ms de la fin de l'effet).

### Grands donjons (60×60) : ce qui coûtait, ce qui a été fait
Mesures sur un 61×61 (308 monstres, 1 601 torches) avec `tools/perf_big.gd` et `tools/prim_census.gd` :
- **`Combat.monster_at`** parcourait tous les monstres à chaque appel (2,2 ms par `in_combat()`, appelé par chaque écouteur de `ctrl.changed` : 41 ms par pas). Il lit maintenant un index case → monstre (`_cell_idx`, refait à chaque image, à chaque déplacement ou apparition via `mark_monsters_dirty`, et revérifié à la lecture) : 8 µs, `ctrl.refresh` 0,3 ms.
- **`Wanderers._tick`** (toutes les 0,5 s) refaisait la liste des cases occupées et la liste des pièges pour chaque monstre : 100 ms. Un cache par pas (`_occ`, `_trap_cells`, `_apart_fast`) donne 6 à 8 ms, avec **exactement** les mêmes déplacements (même ordre des tirages ; `tools/check_wander_equiv.tscn` compare avec les parcours d'origine via `force_slow`).
- **Rendu** : le décor est découpé en blocs de 8×8 cases (`LevelBuilder.CHUNK`), un maillage par bloc, et les torches en lots par bloc (`TorchLayer._build_batches`) : seuls les blocs vus par la caméra sont dessinés. Les torches 3D (512 triangles pièce, 1,4 M de triangles au total sur ce niveau) ne sont de plus dessinées que dans 60 u autour de la caméra (`BODY_RANGE`, ×distance de vue). Triangles par image : 1,5 M → 0,4 M.
Le découpage en blocs change très légèrement l'éclairage (les lumières sont choisies par maillage).

### Critique, esquive, garde : provenance des bonus affichés
Critique ← Dextérité (équipement compris) + talents + capacités de rareté des objets (+ effet d'ensemble mythique) + bonus de critique des modificateurs de partie ; esquive ← Dextérité + capacités « esquive » ; garde ← Constitution. `Stats.crit_total` est l'unique formule du critique (combat et tous les affichages : fiche, infobulles, boutique, dock). Les cartes de `StatExplain` listent maintenant, pour chaque objet, son bonus de Dextérité et sa capacité de rareté (`_sources(…, perk)`), l'ensemble mythique et les modificateurs de partie. Test : `tools/check_stat_items.tscn`.

### Détail des résistances et des capacités d'objets
`StatExplain.data` accepte `res_<école>` (`_resist_section` : bonus de classe `Resist.CLASS_RESISTS`, somme des `resists` des objets équipés, total borné −50 / +90) et `perk_<id>` (`_perk_section` : `Rarity.perk_sum` et les objets qui portent la capacité, via `_sources`). `PartyModal._combat_grid` liste toujours les six écoles et les sept capacités, chacune avec son `StatTip`. Test : `tools/check_stat_details.tscn`.

### Statuts d'un groupe de monstres : par membre
Les statuts (brûlure, poison, gel, sommeil, ralentissement…) vivent sur le **porteur** : le monstre seul, ou chaque membre d'un groupe (`members[i].statusEffects`), jamais sur le groupe. `Combat._hit_holders` donne les membres touchés (le membre visé, ou tous si le sort est de zone) et `_hit_monster` applique le statut à chacun (un jet de chance par membre) ; la berceuse (`sleepGroup`) vise tous les membres vivants. `monster_act` décompte les statuts du membre qui agit (`tick_monster(def, st, holder)`), la brûlure ronge ses PV et peut le tuer seul ; le groupe tombe au dernier membre. Vitesse, réduction de dégâts et résistance réduite lisent le porteur. Affichage : aura par membre (`CombatStage._sync_auras`), statuts par ligne de membre dans la fiche du monstre. Avant, un statut posé sur un groupe frappait un compteur de PV du groupe que les coups ne touchent pas, et se décomptait une fois par membre. Les sauvegardes d'avant gardent un éventuel statut sur le groupe, sans effet. Test : `tools/check_group_status.tscn`.

### Génération du donjon derrière l'écran à l'épée
`GeneratorDialog._generate` n'ouvre plus de fenêtre « Création du donjon » : elle appelle `Loader.generate(builder, on_done)`. L'écran de chargement s'affiche, `DungeonGenerator.build_config` tourne sur un fil de travail (`WorkerThreadPool`, comme la synthèse des sons) pendant que l'épée continue de s'animer (progression douce jusqu'à 3,5 %), puis `on_done` lance la partie (`Data.launch` → `Loader.go`) sur le MÊME écran (`_keep_screen`, sans le recréer ni remettre la barre à zéro). Mesure sur un 40×40 de 8 niveaux (3,5 s de calcul) : pire image 18 ms. Seule la génération non graînée passe par là ; les parties classées (`Seeds`, graine globale) gardent leur chemin. Test : `tools/check_gen_loading.tscn`, mesure : `tools/perf_gen.tscn`.

### Indicateur de zoom de la mini-carte
`Minimap._draw_zoom_ui` écrit un petit texte discret (« Molette : zoom / dézoom ») en bas de la carte quand le zoom est possible (`_max_zoom() > 1`, carte d'au moins 20 cases, hors plein écran). Texte seul : aucun bouton, aucune modification de la taille ni de la logique du zoom (molette et double-clic inchangés).

### Bonus et effets (fiche d'inventaire)
`BonusOverview.build(c, cfg)` regroupe tout ce qui améliore un héros en sept groupes (caractéristiques, combat, résistances d'école, capacités des objets + ensemble mythique, talents, statuts actifs, classe / Constitution / modificateurs d'expédition) en réutilisant les sections de `StatExplain.data` : valeur finale, puis chaque source (objet et emplacement, talent, statut, classe). Les effets sans source sont résumés en une ligne « sans effet ». `EquipDock._add_bonus_overview` l'affiche dans le volet « Détails et sorts » ; les libellés qui retournent à la ligne ont une largeur minimale (sinon coupure lettre par lettre). Test : `tools/check_bonus_overview.tscn`.


## Pièges : Effort collectif
`TrapRules.METHODS["exert"]` (💪) est un choix **toujours ajouté** aux méthodes tirées du piège (`TrapModal.open` l'ajoute à `_methods` ; l'offre sauvegardée dans `trapOffer` n'est pas modifiée, donc aucune migration). Chance : `exertBase` (70) + `statBonus` × moyenne de (Constitution − 10) des héros vivants. Coût : `exertStaPct` (35 %) de l'endurance max de chaque héros vivant, limité à son endurance actuelle (`TrapRules.exert_costs`), payé même en cas d'échec ; le résultat part dans `res.sta_list`, appliqué par `Interactions._trap_resolved`. Échec : `_hit_all(exertDmgPct)`. Bouton désactivé (et entrée refusée par `can_input`) si le coût total est nul. Réglages dans `trapSettings` et l'administration (Général).

## Pièges : placement sur le passage obligé
`DungeonGenerator._forced_passage` remonte le plus court chemin départ → sortie (distances de `bfs`), garde les salles libres à au moins 4 cases (Chebyshev) du départ et de la sortie, les mélange, puis ne retient (jusqu'à 6) que celles dont le blocage (`bfs(..., block)`) coupe la sortie : seules ces cases sont testées, d'où un coût négligeable (génération max ~230 ms en 25×25). `_one_level` y pose les 2–3 pièges (fléchettes : seulement sur une case adossée à un mur, sinon des pointes). S'il ne reste aucune case, le piège est remplacé par un objet ramassable (potion de soin ou d'endurance, armure ou bijou). Test : `tools/check_trap_pass.tscn`. Les donjons générés à partir d'une graine ne sont plus identiques à ceux d'avant ce changement.

## Village en 3D réaliste, tout en longueur
`Village.build_level` fabrique un village de 15 × 45 cases : rue centrale de 3 cases (colonne 7) entre deux portes d'arche (haut : donjon suivant ; bas : retour), place pavée de 7 × 9 cases au milieu (départ au centre, face au nord), douze maisons de 3 × 3 cases réparties de chaque côté (cases pleines `#`, on les contourne), allées de terre vers chaque porte, trois PNJ (marchand, forgeron, maître des talents) sur le pourtour de la place, arbres semés dans les jardins (rangée plus dense le long des barrières, abords des portes dégagés). La clé `houses` (x, y, w, h, face, kind) décrit chaque maison ; `streetX` donne la colonne de la rue ; `plazaCells` les cases pavées. Tirages : flux « village » (type de maison, ordre des PNJ, arbres).
`VillageKit` (`scripts/dungeon/village_kit.gd`) habille le tout avec de vrais matériaux PBR tirés des packs fournis : briques (Bricks085), roche (Rock064), terre (Ground067), herbe (Grass002), pavés (PavingStones138), ardoise (PavingStones127), bois (Wood075), feuillage (LeafSet017 : couleur et opacité réunies dans `feuille_albedo_alpha.png`, découpé par seuil). Jeux de textures : `assets/themes/village_hd/` (2048 px, taille d'origine) et `village_lite/` (1024 px), choisis comme la pierre selon le réglage « Textures » ; `village_lite` est exclu des exports. Fabriqués par `tools/gen_village_textures.py` (`<partie>_albedo.jpg`, `_normal.png`, `_orm.jpg` : R occlusion, G rugosité) à partir des packs dézippés, plus les textures de la maison à colombages (`beton`, `toit_m`, `bois_m`).
- Maisons (`VillageKit.houses`) : trois types. « timber » : modèle fourni `assets/village_models/maison_beton.fbx` (concrete_house_004, LOD1) avec ses textures ; « brick » : maison de briques à toit d'ardoise construite en code (porte, fenêtres à volets, cheminée) ; « ruin » : modèle fourni `maison_brique.fbx` (ruine, pièces `Cube` et `Cube_028` seulement). Les modèles sont recentrés, mis à l'échelle (parcelle, hauteur plafonnée) et posés au sol dans un pivot (`_model`) ; leur façade regarde vers la rue (`TIMBER_YAW` règle l'orientation du modèle à colombages).

La caméra voit jusqu'à 300 u dans le village (`Main._apply_outdoor`).
- Ciel et lumière : ciel procédural `village_sky.gdshader` (dégradé zénith/horizon, soleil, lune, étoiles, nuages en bruit fractal ; direction et couleurs passées en uniforms), `Outdoor.apply_environment` (ambiance tirée du ciel, brume d'horizon, rendu filmique), `DirectionalLight3D` à ombres en quatre cascades (`Outdoor.decorate`), SSAO et réglage couleur (`VisualFx`) activés aussi en extérieur. Arbres des jardins : `VillageKit.tree_mesh` (tronc texturé, cartes de feuilles découpées, `ALPHA_TO_COVERAGE` pour lisser les bords avec le MSAA).

État statique (`clock`, `rain`) : le cycle continue entre deux passages (journée de 20 min en automatique, pluie par intervalles). Réglages `Settings.village_time` (auto, aube, jour, crépuscule, nuit) et `village_weather` (auto, beau, pluie). Purement visuel : aucun appel à `GameRng`, aucune entrée enregistrée, donc rediffusions inchangées. Pas de son de pluie (aucune ressource sonore).

La case reste bloquante : on lui parle en la heurtant, mais l'étal est avancé de 0,9 u vers la rue (bord de sa case) pour que le groupe s'arrête tout près. ## Salles et couloirs
**Génération** (`DungeonGenerator`) : `plan_rooms(mw, mh)` tire des rectangles de cases du labyrinthe (2×2 à 3×3, jamais sur le départ, séparés d'au moins une case, au plus `ROOM_BUDGET` = 30 % des cases, répartis par « meilleur éloignement sur 14 essais »). `carve_maze_rooms` ouvre chaque rectangle entier et le traite comme UNE unité dans le parcours en profondeur : le niveau reste connecté et les salles sont reliées par les couloirs que le parcours choisit (plus 12 % de boucles). `_room_mask` (cases de sol des salles) sert à `_one_level` : la sortie (`far`) est toujours un couloir, une porte verrouillée n'est jamais au milieu d'une salle (`_try_locking_door`). Le reste du placement (monstres, objets, pièges sur le passage obligé, marchand) est inchangé et travaille toujours sur les cases du labyrinthe.
**Styles de salle** (visuels seulement, aucun effet sur le jeu ni le rejeu, rien de stocké dans les sauvegardes) : `RoomStyles.assign(level, rooms, theme)` donne un style à chaque salle (`RoomMap.detect`), par ordre de priorité : choix de l'éditeur (`level.roomStyles`, clé « x,y » du coin haut-gauche), contenu (salle d'un monstre `isBoss` → `repaire`, du marchand → `marche`, salle la plus riche en coffres et toute salle de 2 coffres ou plus → `tresor`), sinon tirage pondéré par thème (`THEME_WEIGHTS`) parmi `GENERAL` en excluant le style de la salle précédente (ordre haut-gauche) et en pénalisant les styles déjà utilisés ; une petite salle (moins de 9 cases ou moins de 3×3) n'a pas les styles encombrants (`BIG_STYLES`). Hachage de la position et de l'identifiant du niveau, jamais `GameRng`. `RoomStyles.vedette` : la plus grande salle reçoit toujours sa pièce maîtresse (une chance sur trois pour les autres). `RoomProps.plan(ctx)` (aucun nœud, testable) renvoie des primitives (`box`, `cyl`, `sph`, `cone`), des flammes et des toiles ; règle d'or : accessoires contre les murs (un pan de mur n'en porte qu'un, les grands seulement sur les cases où x + y est impair, les torches étant sur les cases paires), jamais sur une case portant un objet, un escalier, le marchand ou le départ, jamais au centre d'une case ; la pièce maîtresse occupe un sommet entre quatre cases (le pilier de ce sommet disparaît). `RoomDecor.add` transforme le plan en `MultiMesh` groupés par matériau et forme, ajoute un sol par style (textures procédurales mises en cache), piliers (brisés pour `ruine`), tapis, lustre, bannières (qui évitent les pans déjà pris), flammes billboard et une ambiance `CPUParticles3D` (8 à 28 particules par salle, compatible export Web). Palettes propres au trésor (doré) et au repaire (sang). Éditeur : `AdminLevels._room_styles_section` (onglet Réglages) liste les salles détectées avec leur style automatique. Tests : `tools/check_room_styles.tscn` (déterminisme, contenu, variété, accessoires jamais au centre d'une case ni sur une case occupée, choix de l'éditeur).

**Compatibilité des rejeux** : `DungeonGenerator.legacy_layout` (vrai = ancien labyrinthe, aucun tirage de salle, mêmes graines qu'avant) est posé par `ReplayLive` et par `tools/replay_run.gd` (entrée facultative `game_version`) pour les parties enregistrées avant la 1.37.0. Les sauvegardes stockent la carte : aucune migration.
**Repérage** (`RoomMap.detect(rows)`) : une salle est une zone de sol d'au moins 2×2 cases et 6 cases au total, d'après la seule carte : les salles dessinées dans l'éditeur sont donc reconnues comme les générées (l'éditeur n'a plus de limite ni de case « salles »).
**Décors** (`RoomDecor.add`, appelé par `LevelBuilder.build` hors village) : piliers sur les sommets entre quatre cases (jamais dans une case), tapis à plat, lustre au plafond, bannières sur les pans de mur sans torche ; choix déterministes (hachage de la position et de l'id du niveau), sans toucher au hasard du jeu. Purement visuel : aucun effet sur les déplacements, le combat ni le rejeu. Test : `tools/check_rooms.tscn`. Toutes les flammes des décors (lustre, bougeoirs, braseros, appliques, cheminée, lanternes, champignons) reprennent celles des torches de couloir : `RoomDecor._flame` empile les points, `_flush_flames` les regroupe en MultiMesh par couleur avec la goutte 3D animée par shader, le cœur et le halo de `TorchLayer` (mêmes matériaux partagés) ; couleur du thème comme les torches, ou verte / rouge / dorée pour les styles à flamme colorée.

## Coffres
Objet de niveau `{"type": "chest", "wall": "N|E|S|O", "gold": n, "contents": [objets]}` (les objets du contenu sont des objets de sol complets, tirés avec la source de rareté `chest` de `Rarity.weights` ; ils ne sont PAS dans `items` du niveau). Test : `tools/check_chest_tool.tscn`. Aucune migration de sauvegarde (états additifs).
