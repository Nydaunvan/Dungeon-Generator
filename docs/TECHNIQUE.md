# Documentation technique

Détails pour développeurs : structure du projet, vérifications, publication, partie en ligne (Supabase) et rejeu vérifié. Retour à la [présentation du jeu](../README.md).

Jeu en GDScript sous Godot Engine (rendu Forward+ (Vulkan, repli OpenGL si Vulkan est absent) ; versions exécutables Windows et Linux uniquement, le Web est abandonné).

## Structure
- `data/` : données du jeu (config par défaut, talents, constantes, textes, niveaux de qualité)
- `assets/` : textures des 7 thèmes, icônes, portraits, planches (monstres, objets, torches)
- `scripts/core/` : chargement des données (autoload `Data`)
- `scripts/rules/` : moteur de règles sans affichage (formules de stats, puis combat, statuts…)
- `scenes/` : scènes Godot
- `data/quality_presets.json` : niveaux graphiques Faible / Moyen / Élevé / Ultra (menu « ⚙ Paramètres », autoload `Settings` : détection de la machine et adaptation automatique)

## Utilisation
Cloner le dépôt, ouvrir `project.godot` dans Godot 4.7, lancer le projet (F5).

## Sous-dossiers
- `scripts/rules/` : règles sans affichage (personnages, combat, générateur de donjon, état de partie, hasard et horloge déterministes, journal d'actions).
- `scripts/dungeon/` : couloir 3D (murs, portes, torches, brouillard, fontaines, sprites des monstres, salle de combat).
- `scripts/game/` : liaison entre règles et affichage (combat, actions, pièges et fenêtres de décision, monstres errants).
- `scripts/ui/` : fenêtres et interface (sac, forge, paramètres, comptes, défis, chat…).
- `scripts/core/` : services (données, textes, réglages graphiques, sauvegardes, son, mise à jour, compte en ligne, rejeu).
- `scripts/admin/` : éditeur de donjon et outils d'administration.
- `scenes/` : démarrage, accueil, partie, administration.
- `data/lang/` : textes français et anglais, guide et tutoriel ; `data/cloud_config.json` : configuration publique du compte en ligne.
- `assets/themes/` : textures des sept thèmes de décor (murs, sols, plafonds, fontaine) ; `monsters/` : sprites des monstres et boss ; `portraits/` : portraits des héros ; `icons/` : icônes d'objets, de sorts et de classes ; `ui/` : cadres, boutons, emplacements ; `home/` : écran d'accueil ; `fonts/`, `music/`, `sounds/` ; `sheets/` : planches d'objets et de monstres ; `misc/` : textures diverses (dont l'étal du marchand).
- `assets_src/` : images sources de l'épée (taille d'origine) ; seules les versions retaillées de `assets/ui/` sont exportées.
- `supabase/migrations/` : un fichier SQL par évolution du schéma, à appliquer dans l'ordre.
- `tools/` : `check_*` vérifications, `shot_*` captures, `gen_*` et `make_icon.py` génération de ressources, publication (versions, notes, paquets, VirusTotal), vérificateur des parties classées.
- `export_presets.cfg` : généré par `tools/gen_export_presets.py`.

## Vérifications
- Compilation : `godot --headless --path . res://tools/check_compile.tscn`
- Fenêtre de compte (sans réseau) : `godot --headless --path . res://tools/check_account.tscn`
- Textes : `python3 tools/check_lang.py`
- Réglages graphiques : `godot --headless --path . res://tools/check_settings.tscn`
- Mise en page mobile (aucun débordement à droite, carte masquée) : `godot --headless --path . res://tools/check_mobile.tscn`
- Touches du clavier (défauts par langue, réassignation, conflits, onglet Commandes) : `godot --headless --path . res://tools/check_keys.tscn`
- Effets de sorts avancés (choix de l'effet, repli, anciens sorts, paliers, lancer de chaque effet) : `xvfb-run -a godot --rendering-driver opengl3 --path . --script res://tools/check_spell_fx.gd`
- Version et journal : `python3 tools/check_version.py`
- Compte en ligne (sans réseau) : `godot --headless --path . res://tools/check_cloud.tscn`

## Versions et publication
- Le numéro de version est dans `project.godot` (`config/version`, forme `1.30.1`, ou `1.30.1-test1` pour un build de test). Le jeu l'affiche à partir de là (`AppVersion`).
- Journal des versions : `data/changelog.json` (affiché dans le jeu). Les notes de la publication GitHub en sont tirées (`tools/release_notes.py`).
- Publier : pousser sur `migration/donnees` un commit dont le message contient `[exe]` (préversion `v<version>`) ou `[release]` (publication normale). Le workflow « Publication » exporte Windows et Linux en **exécutable + paquets** (voir ci-dessous), crée ou met à jour la publication et y joint : l'installateur Windows (`...-setup.exe`), les installations complètes (`...-windows-full.zip`, `...-linux-full.tar.gz`), les fichiers un par un (`exe-*`, `core-*.pck`, `themes.pck`, `monsters.pck`, `audio.pck`) et les manifestes `manifest-<plateforme>.json` lus par la mise à jour du jeu.
- Disposition d'une installation : `Dungeon Generator.exe` (moteur seul) + `Dungeon Generator.pck` (code, données, polices, interface) + `packs/*.pck` (gros assets) + `install.json` (état des fichiers). Les groupes de paquets sont définis dans `tools/gen_export_presets.py` (qui régénère `export_presets.cfg`) ; `scripts/core/pack_loader.gd` monte `packs/*.pck` au démarrage.
- Mise à jour partielle (`scripts/core/updater.gd`) : le jeu lit le manifeste de la dernière publication et ne télécharge que les fichiers dont l'empreinte de contenu a changé. Essai complet : `sh tools/check_update_e2e.sh` (variable `GODOT`).
- Il n'y a plus d'export Web : le workflow d'envoi FTP a été supprimé (le site déjà en ligne n'est plus mis à jour).

## Partie en ligne (Supabase)
- Le jeu reste jouable hors ligne : rien n'est appelé au lancement. Le module de compte est l'autoload `Cloud` (`scripts/core/cloud.gd`) ; sa configuration (URL du projet + clé **publique**) est dans `data/cloud_config.json`. La clé secrète (`sb_secret_…` / `service_role`) ne va jamais dans le dépôt ni dans le jeu.
- Le schéma de la base est versionné dans `supabase/migrations/` (à appliquer dans l'ordre dans le SQL Editor du projet Supabase) : profils (pseudo public), donjons partagés (code DGZ1), signalements, challenges, parties soumises et classement. Les règles d'accès (RLS) bornent tout ce que la clé publique peut faire.
- Classement : le jeu envoie la graine et le journal d'actions de la partie (`runs`, statut `pending`), jamais un score cru sur parole. Un vérificateur de confiance, qui détient la clé secrète hors du dépôt, rejoue la partie et inscrit le score recalculé (`verified`) ; seul le classement des parties vérifiées est public (`leaderboard`).
- Défis (donjon aléatoire) : cliquer sur « Donjon aléatoire » ouvre d'abord la fenêtre des défis en cours avec leurs classements (`scripts/ui/challenges_modal.gd`), puis « Lancer un donjon aléatoire » mène aux réglages habituels. Un défi `declared` concerne les donjons aléatoires (pas de graine commune, donc pas de rejeu) : le jeu **déclare** son score (`scores`) et la base le borne par des contrôles de plausibilité (au moins 10 s de jeu par niveau, score qui ne baisse jamais, limites par jour) ; le classement public (`classement`) distingue les scores vérifiés (✔) des scores déclarés. Le suivi de partie (`levelsCleared`, `playSeconds`, `runId`, `adminUsed` dans `gs.stats`) et l'envoi sont dans `scripts/core/challenges.gd`. Une partie où l'administration a été ouverte n'est jamais envoyée. Un score trop incohérent se retire depuis le tableau de bord Supabase (table `scores`).
- Tests sans réseau : `godot --headless --path . res://tools/check_cloud.tscn` (compte), `res://tools/check_account.tscn` (fenêtre de compte), `res://tools/check_challenges.tscn` (défis, classement, envoi du score) ; suivi d'une vraie partie (affichage ou Xvfb requis) : `--script res://tools/check_run_tracking.gd`.
- Rejeu vérifié (en cours, étapes 1–4 faites) : toute la partie découle d'une graine texte (`Seeds`, `GameRng` : flux nommés combat/loot/trap/wander/village/ids, état sauvegardé avec la partie) et d'une horloge de jeu (`GameClock`, jamais l'heure réelle). Les actions du joueur sont journalisées dans `gs.run_log` (`RunLog`, entrées `[ms, commande, …]`) : déplacements, combat, objets (`Actions`), forge et Maître des Talents (village), et toutes les fenêtres de décision (`Flows` : fontaine, talents, évolution, piège et ses puzzles, boutique, marchand, victoire, village, modificateurs). Toute action non journalisée marque la partie « souillée » (`RunLog.unrecorded`) : elle n'est alors jamais classée. Le rejeu (`scripts/core/replayer.gd`) fait tourner la vraie scène du jeu et y injecte les commandes ; les règles d'acceptation vivent dans la logique partagée, pas dans l'interface. Tests : `check_determinism.tscn`, `check_game_rng.tscn` (valeurs de référence à confirmer sous Windows), `check_clock.gd`, et `xvfb-run -a godot --path . --script res://tools/check_replay.gd -- <graine> <actions> <niveaux>` (un bot joue une vraie partie, puis le journal est rejoué : l'empreinte de l'état doit être identique). Restent : règles des parties classées (ni administration, ni sauvegarde manuelle, ni retour arrière), vérificateur serveur et classement vérifié par mode de jeu.
- Parties classées par difficulté (serveur, étape 6a, pas encore branché à l'interface) : `supabase/migrations/20261010000200_parties_classees.sql` (réglages par difficulté `ranked_modes`, parties `ranked_runs`, fonctions `start_ranked_run` / `submit_ranked_run`, vue `classement_difficulte` vide tant que rien n'est vérifié). Côté jeu : `scripts/core/ranked_run.gd` (configuration partagée avec le vérificateur, démarrage, envoi, classement). Vérificateur : `tools/replay_run.gd` (rejoue un journal) + `tools/verify_runs.py` + workflow `.github/workflows/verify-runs.yml` (toutes les 15 min, secrets `SUPABASE_URL` et `SUPABASE_SECRET_KEY`, chaque partie est rejouée avec les règles de sa version, étiquette `v<version>`). Une partie classée n'accepte ni administration, ni export/import ; sa sauvegarde est à usage unique.
- Hardcore du mois (étape 6b) : `supabase/migrations/20261010000300_hardcore_mensuel_et_recompenses.sql`. Une graine par mois tirée par le serveur à la première partie du mois, difficulté hardcore, UN essai par jour (jour de Paris, consommé au lancement), classement `classement_periode` des parties vérifiées. Récompenses uniquement cosmétiques et de l'expérience : catalogue `badges` (titres, cadres, couleurs de pseudo), `player_badges`, `xp_log` / vue `account_xp` (niveau de compte), `player_cosmetics` + `equip_cosmetics`. Le vérificateur attribue tout (`award_run` après chaque partie vérifiée, `close_due_periods` pour les badges de rang des mois terminés depuis 2 jours), une seule fois. Côté jeu : section « Hardcore du mois » dans la fenêtre des défis du donjon aléatoire (`challenges_modal.gd`), `RankedRun.launch` / `submit` (journal gardé hors ligne puis renvoyé). Écrans : « Mes récompenses » (`rewards_modal.gd` : niveau de compte, collection de badges, équipement du titre, du cadre et de la couleur), « Parties classées » (`ranked_modal.gd` : un classement par difficulté + lancement), plaques de pseudo avec cadre (`cosmetics.gd`), accessibles depuis la fenêtre des défis et le compte. Tests sans réseau : `xvfb-run -a godot --path . --script res://tools/check_ranked_flow.gd` et `check_rewards_ui.gd`.
- Super admin (étape 6c) : `supabase/migrations/20261010000400_super_admin.sql`. Le rôle est une ligne de la table `admins` (aucune politique : illisible et inscriptible depuis le jeu ; on l'accorde par SQL depuis le tableau de bord : `insert into public.admins (player_id) values ('<uuid>')`). Chaque fonction `admin_*` revérifie le rôle côté serveur (`is_super_admin()`, erreur `acces_refuse`) : un jeu modifié n'obtient rien. Parties classées de TEST (`admin_start_ranked_run`, colonne `ranked_runs.test`) : n'utilisent pas l'essai du jour, exclues des classements, de l'XP, des badges et de la clôture des mois, mais rejouées par le vérificateur ; le Hardcore du mois de test garde les réglages du mois avec une graine aléatoire (la vraie graine n'est jamais révélée). Statistiques en lecture seule : `admin_overview`, `admin_players`, `admin_runs` (ni courriels ni journaux d'actions), et `admin_purge_tests`. Côté jeu : bouton « Super admin » dans la fenêtre Compte (affiché seulement si le serveur confirme le rôle), `super_admin.gd` / `super_admin_modal.gd`. Test sans réseau : `xvfb-run -a godot --path . --script res://tools/check_super_admin.gd`.

## Effets de sorts
- L'effet visuel d'un sort est indépendant de son `style` (école : le style décide aussi de la logique de combat, magique ou physique). Trois champs sur le sort : `fx` (identifiant d'effet, `classic` = effet d'origine en sprites, vide = effet par défaut du style), `fxTint` (couleur HTML, vide = couleur d'origine) et `fxPower` (0,6 à 2). `Data.ensure_defaults` les ajoute aux anciens sorts et aux sauvegardes.
- `scripts/dungeon/spell_fx_library.gd` (`SpellFxLibrary`) : catalogue des effets avancés (id, style et mode compatibles, script), teintes et intensités proposées, résolution de l'effet (effet inconnu ou incompatible = effet par défaut du style), palier de qualité, point d'entrée `cast`. `combat.gd` et `main.gd` y passent ; l'effet d'origine reste `SpellFxStyles.cast_spell`. Ajouter un effet = une entrée du catalogue + le script (une classe qui étend `SpellFxStyles` avec une méthode `play(spell_id, target, ctx)`) + les textes `admin.spells.fx_*`.
- Paliers (`SpellFxLibrary.tier`, d'après les options graphiques) : 0 sans halo (`fx_glow` désactivé) = effet d'origine ; 1 = particules GPU, halo HDR ; 2 = + lumière dynamique qui éclaire la brume, rune au sol (option `fx_decals`) ; 3 (Ultra, `particles` ≥ 1,25) = + lentille de distorsion. Rendu non Forward+ : effet d'origine. Le script de l'effet est chargé à l'exécution ; s'il ne se charge pas, l'effet d'origine joue à la place.
- `scripts/dungeon/spell_fx_arcane.gd` (palette violette de base tournée par défaut vers le bleu, `DEFAULT_HUE`) : cristal, orbe de mana et rayon (shaders d'onde de choc, de lentille, d'orbe et de rayon ; rubans de particules GPU ; décalque de cercle runique (futhark ancien dessiné par traits dans une texture 512 px, couleur multipliée par l'opacité car l'émission du décalque ignore l'alpha) ; secousse de caméra désactivée par « mouvement réduit »). Le contrat avec le combat est conservé (`SpellFx3D.busy`, `wait_idle`) ; les shaders sont précompilés par `warm_up.gd`.
- Éditeur : colonne « Style (animation) » de l'onglet Sorts (`admin_spells.gd`) avec effet, teinte, intensité et bouton « Aperçu » (`scripts/ui/spell_fx_preview.gd` : petite scène 3D, effet joué en boucle avec les réglages graphiques actuels).
- Les capacités spéciales des monstres (sorts de dégâts tirés au hasard) ne jouent pas d'effet de sort, seulement l'animation du coup reçu.

## Commandes (couloir 3D)
Boutons à l'écran (tactile) ou clavier, touches physiques : ↑/Z avancer, ↓/S reculer, Q/D pas de côté, ←/A et →/E tourner (libellés AZERTY).

## Icône du jeu
- Source : l'épée du jeu (`assets/ui/sword_loading_padded.png`) ; `python3 tools/make_icon.py` régénère `assets/app_icon.png` (icône du projet : fenêtre et barre des tâches sous Windows et Linux), `installer/app.ico` et `installer/app_icon_256.png`.
- Windows : le workflow de publication applique `installer/app.ico` et les informations de version à l'exécutable avec rcedit sous Wine (`tools/patch_windows_exe.sh`, vérifié par `tools/check_exe_icon.py` : simple avertissement en cas d'échec) ; l'installateur Inno Setup, ses raccourcis et la désinstallation utilisent la même icône (`installer/app.ico`).
- Linux : l'exécutable ELF ne porte pas d'icône ; l'archive complète contient `Dungeon Generator.png` et `install-menu.sh` (entrée du menu des applications avec l'icône, sans droits administrateur ; `--remove` pour la retirer).


### Compteur de performances
`scripts/core/perf_overlay.gd` : un seul `Label` (couche 120) en haut à gauche, sans panneau ni cadre ; lisibilité assurée par un liseré de texte sombre. Une ligne : images/s, RAM, VRAM, appels de dessin (couleur selon les images/s). F3 ou bouton 📊.
Taille constante : la ligne est compensée par le rapport entre l'échelle de la scène de jeu (zone de conception 1600 x 1000) et l'échelle courante (`content_scale_factor`), donc elle garde la taille qu'elle a dans le donjon au lancement et dans le menu d'accueil.

## Pièges : pointes au sol
`scripts/dungeon/trap_spikes.gd` (`TrapSpikes`) : le piège `spikes` est un vrai volume, plus un décalque. Un maillage unique (`ArrayMesh`, construit par `SurfaceTool` puis partagé par tous les pièges) : surface 0 = plaque de fer biseautée, rivets et douilles (normales explicites) ; surface 1 = 25 pointes d'acier à trois anneaux (hauteurs et inclinaisons variées, dégradé rouille → acier, quelques-unes tachées de sang), normales lissées. Elles projettent des ombres sous la lumière des torches. Une ombre de contact douce (texture générée) noircit le sol autour. `TrapDecals.make_mesh("spikes")` y renvoie ; les autres pièges (fléchettes, fosse, vapeurs) restent des décalques.
Les pointes forment un nœud enfant `Spikes` : quand le piège est désamorcé (`Interactions._trap_resolved`), `EntityLayer.disarm_item` appelle `TrapSpikes.retract` (écrasement progressif en 0,5 s dans la plaque, qui reste en place) ; au chargement d'un niveau (`main.gd`), l'état « désamorcé » des sauvegardes rentre les pointes tout de suite, sans animation, donc rien à migrer. Les autres pièges disparaissent comme avant.

## Pièges : vapeur verte
`scripts/dungeon/trap_gas.gd` (`TrapGas`) : bouche d'aération de fer (maillage `SurfaceTool`, mêmes briques `TrapSpikes.add_box` / `add_prism`) et nuage vert épais en continu : trois émetteurs `GPUParticles3D` (colonne de volutes, nappe rasante qui coule sur le sol, cœur lumineux additif en HDR pour le halo de l'environnement), turbulence, bouffées en texture de nuage générée (bruit simplex), `proximity_fade` (Forward+) pour estomper les bouffées au contact du sol et des murs ; lueur verte pulsante (`OmniLight3D`) et brume volumétrique verte (`FogVolume`, Forward+ uniquement). Le nombre de particules suit l'option `particles`. Les particules sont préchauffées (`preprocess`) : le nuage est déjà formé à l'apparition. `TrapGas.stop` (piège désamorcé, `EntityLayer.disarm_item`) coupe les émetteurs, éteint la lueur et dissipe la brume en quelques secondes ; au chargement d'un niveau déjà désamorcé, le nuage n'est pas créé. `warm_up.gd` précompile les deux pièges.

### Sons des pièges qui se déclenchent
Un son propre à chaque type de piège, joué quand le jet de dés échoue (échec simple ou critique) : `Sound.TRAP_FAIL_SOUNDS` (`spikes` → `trap_snap.ogg`, `gas` → `steam_hiss.ogg`) ; un type sans son attitré joue le coup habituel (`hit`). `Sound.trap_fail(kind)` est appelé par `TrapModal._roll_outcome` avec le type du piège ; la sonde ratée ne déclenche pas le piège et ne joue donc rien de particulier. Chaque fichier est converti du MP3 fourni en OGG et atténué à l'export pour atteindre -20 LUFS (comme `dice.ogg`), avec un gain `SFX_GAIN_DB` de -14 (même méthode que tous les effets : cible -34 LUFS, `tools/sfx_levels.py`). Règle pour tout nouveau son : le mesurer avec `tools/sfx_levels.py` et reporter son gain dans `SFX_GAIN_DB`.

Parcours des récompenses (onglet « Récompenses » du hub en ligne, `online_hub.gd`, `_rw_render`) : les récompenses déjà obtenues par le joueur sont listées en premier, puis celles à obtenir ; dans chaque groupe, par rareté croissante, puis dans l'ordre du catalogue.
